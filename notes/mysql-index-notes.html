01

索引的地基：存储引擎与索引的关系

讲索引之前，先要弄清一件事：索引不是 MySQL「Server 层」的语法糖，而是存储引擎负责落地的数据结构。 同一个 CREATE INDEX 语句，交给 InnoDB、MyISAM、MEMORY 执行，底层的组织方式完全不同。

一、存储引擎是什么

MySQL 是「两层」结构：上一层负责连接、解析 SQL、优化，这些工作和用什么引擎无关；下一层才是存储引擎，负责把数据写到磁盘、再从磁盘读回来。可以把 MySQL 想成一台电脑，引擎就是里面的硬盘——查询交给谁去落实，取决于这张表装的是哪个引擎。

存储引擎是跟表走的，不是跟库走的。同一个库里，A 表可以用 InnoDB，B 表也可以用 MEMORY，互不影响。一条查询从进来到落地，依次经过：

  1. 连接器：校验账号密码、分配连接，后续这条连接上的权限都在这里判定。
  2. 分析器：词法、语法分析，把 SELECT ... WHERE name = '吕布' 拆成「查哪张表、有哪些条件」。
  3. 优化器：决定用哪个索引、多表连接的顺序，这一步的产物就是后面 EXPLAIN 看到的执行计划。
  4. 执行器：按执行计划调用存储引擎的接口，由引擎去 B+ 树里定位数据页、读出记录。
📌 记住这条分工 Server 层只负责解析 SQL、选执行计划；真正存取数据、维护索引结构的是存储引擎层。 所以「索引怎么存、能不能用上」，最终由表的存储引擎决定。

三、当前默认引擎：InnoDB

MySQL 从 5.5 版本起就把 InnoDB 定为默认引擎，8.0 一路默认至今：建表不写 engine= 就是 InnoDB；show engines; 里 InnoDB 那行的 Support 显示 DEFAULT，select @@default_storage_engine; 也会直接返回 InnoDB。 所以前面练习用的 tb_user、emp、dept 实际上全是 InnoDB。

四、InnoDB 的聚簇索引与二级索引

正因为默认引擎是 InnoDB，索引才呈现出下面这两棵树的结构——这也是 InnoDB 与 MyISAM 最本质的区别：

聚簇索引 数据即索引

InnoDB 把整张表按主键组织成一棵 B+ 树，叶子节点直接挂完整的一行数据。所以按主键查，找到叶子就拿全了。

二级索引 叶子挂主键

普通、唯一、联合索引都是二级索引，叶子节点只存「索引列的值 + 主键 id」。要拿其他列，还得拿 id 回聚簇索引再查一次，这就是「回表」。

这两棵树的细节会在第 2 章分类和第 4 章 B+ 树里展开，这里先建立「一张表 = 一棵聚簇索引 + N 棵二级索引」的整体图景。

五、三个常见引擎对比

InnoDB、MyISAM、MEMORY 是学习和面试里最常被拿来比较的三个，先把区别一次摆清：

六、逐个认识这三个引擎

InnoDB 现在的主力

  • 支持事务：一组操作要么全成功、要么全回滚，转账这类场景离不了。
  • 支持外键：约束笔记里的 foreign key ... references 只有它能真正生效。
  • 行级锁：改第 1 行时别人还能改第 2 行，并发写能力强。
  • 崩溃恢复：靠 redo log 等机制，突然断电也有机会把数据救回来。

一句话：要安全、要事务、要并发写，选它。

MyISAM 老一代引擎

  • 无事务、无外键：写进去就是写进去了，出错没法回滚。
  • 表级锁：一个人写，整张表其他人只能等着，并发写很吃亏。
  • 纯读略快：结构简单，但现在的硬件上差距不明显。
  • 会记行数：select count(*) from 表; 直接报存好的数字，而 InnoDB 得逐行数——这就是 InnoDB count(*) 相对慢的原因。

一句话：只读的历史系统可能还在用，新项目一般不用。

MEMORY 数据放内存

  • 数据全在内存：读写飞快，但 MySQL 重启 / 关机后只剩表结构。
  • 默认哈希索引：where id = 1 这类等值查询很快，> 这类范围查询反而不好用。
  • 不支持大字段：BLOB、TEXT 都存不了，一般只放小数据。
  • 定位是临时表：中间计算结果先放进去，用完就扔。

一句话：当缓存或临时表用，别拿它存正经数据。

七、怎么选（实际工作中的判断）

  • 拿不准就 InnoDB：它是默认值，绝大多数场景都够用，没必要为了一点查询速度去换 MyISAM。
  • 需要回滚、外键、高并发写：只能选 InnoDB。
  • 纯内存的临时计算：可以考虑 MEMORY，但更常见的做法是用 Redis 之类的缓存，MySQL 里用它的机会不多。
  • 要换引擎：用 alter table 表名 engine=InnoDB;，会重建整张表，数据量大时很慢，最好挑业务低峰做。
SQL · 补充：给已有表切换引擎（会重建表，数据保留） 
-- 把 my_myisam 从 MEMORY 换成 InnoDB（数据保留，但整表重建）
alter table my_myisam engine=InnoDB;

-- 再确认一次引擎是否已切换
show create table my_myisam;
⚠️ 换引擎的代价 alter table ... engine=xxx 会锁表重建：大表上执行前先想清楚能不能接受这段时间的业务影响，务必安排在低峰期。

八、几个容易踩的坑

  • 引擎是表的属性，不是库的属性：改库的默认引擎不会影响已经建好的表。
  • 建表不写 engine= 就是 InnoDB：不用特意去写，写了也只是把默认值重复一遍。
  • MyISAM 上加外键不报错，但也不生效：约束那套东西只有在 InnoDB 上才真的管用。
  • MEMORY 表重启就没数据：拿它做练习没问题，千万别当正式表用。
  • MEMORY 默认哈希索引：只擅长等值查询，>、ORDER BY 这类范围和排序很吃亏。
  • alter table ... engine=xxx 会锁表重建：大表执行前先评估业务影响。

02

索引是什么、怎么分类（本质与代价 → 功能分类 → 物理存储）

一、索引的本质与代价 先想明白再动手

一句话理解：索引（Index）就是数据库表的「目录」——它是帮 MySQL 高效查找数据的排好序的数据结构。

  • 没索引时：像一本没有目录的 1000 页字典，想找某条记录只能从第 1 页翻到第 1000 页（全表扫描），数据越多越慢。
  • 有索引后：先查目录直接定位到目标页码，把全表扫描 O(N) 变成树查找 O(log N)，极大减少磁盘 I/O 次数。

索引带来的好处 收益

  • 大幅加速查询：WHERE 查找速度提升成百上千倍。
  • 加速排序与分组：索引本身有序，能减少 ORDER BY 和 GROUP BY 的额外排序消耗。
  • 保证数据唯一性：主键索引和唯一索引可强制约束手机号、学号不重复。
  • 加速多表连接：大幅提升 JOIN ... ON 关联匹配效率。

索引带来的代价 成本

  • 占存储空间：每个索引都是一棵独立的树，既占硬盘空间，也会占 MySQL 缓存热点数据的内存池（Buffer Pool）。
  • 降低增删改速度：执行 INSERT / UPDATE / DELETE 时，不仅改数据，还要同步维护目录的有序性。
  • 优化器选择成本：索引建得太杂，MySQL 挑索引本身也会多花时间，甚至可能挑错。
💡 核心记忆 索引本质是「以空间换时间、以一点写速度换极致的读速度」。并不是建得越多越好，而是要建在刀刃上！

三、按物理存储方式分类（InnoDB 核心） 进阶必懂

在 MySQL 默认的 InnoDB 引擎里，上述索引在磁盘底层只分为两种存放形式：

聚簇索引（主键索引） 每表唯一

就像字典正文按拼音排好序，叶子节点直接装着整行完整数据（数据即索引）。

  • 一张 InnoDB 表必须有且只有 1 棵聚簇索引。
  • 生成规则：① 有显式主键就用主键；② 没主键就选第一个 UNIQUE NOT NULL 索引；③ 都没有，InnoDB 自动生成隐藏的 6 字节行 ID（DB_ROW_ID）兜底。

二级索引（辅助索引） 可建多个

普通、唯一、联合索引都属于二级索引。像字典前面的“部首检字表”，叶子节点不装整行数据，只装「索引列的值 + 对应的主键 id」。

  • 为什么存主键值而不存硬盘物理地址？因为数据页变动时物理地址会变，存主键值能避免移动一行数据时把所有二级索引的指针全改一遍！
🔍 顺便了解：InnoDB 和老引擎 MyISAM 的索引存储区别 MyISAM 是“非聚簇”的：它的索引文件（.MYI）和数据文件（.MYD）分开存，不管是主键索引还是普通索引，叶子节点存的都是数据行的磁盘物理地址；而 InnoDB 直接把表数据按主键组织成一棵聚簇索引树（存在 .ibd 文件里）。
🧩 补充分类：按数据结构还能这么分 除了「功能」和「物理存储」，索引按底层数据结构还可以分为：B+Tree 索引（InnoDB 默认，能等值也能范围和排序）、Hash 索引（MEMORY 引擎默认，只擅长等值，不支持范围和排序）、Full-text 全文索引（按词检索，用于文章内容搜索）。日常说「加索引」，默认指的都是 B+Tree 索引。
03

索引语法：建、查、删、隐藏（基于 02_索引语法.sql）

这一章的示例统一使用 02_索引语法.sql 里的真实表 itheima.tb_user（24 条用户数据），建库建表的完整语句见本章末尾的动手演练。

一、创建索引的 3 种方式

方式 1：建表时顺手建好（最省事）——脚本里的 tb_user 就是建表时直接写了主键：

SQL · 来源：02_索引语法.sql 
create table tb_user (
    id         int primary key auto_increment comment '主键',
    name       varchar(50)  not null comment '用户名',
    phone      varchar(11)  not null comment '手机号',
    email      varchar(100) comment '邮箱',
    profession varchar(11)  comment '专业',
    age        tinyint unsigned comment '年龄',
    gender     char(1)      comment '性别, 1: 男, 2: 女',
    status     char(1)      comment '状态',
    createtime datetime     comment '创建时间'
) comment '系统用户表';

建表时还能把 UNIQUE INDEX uk_xxx (列)、INDEX idx_xxx (列1, 列2)、INDEX idx_xxx (列(10))、FULLTEXT INDEX 直接写在字段列表后面；本表只保留了主键，其余索引在方式 3 里补建。

方式 2：给已有表加索引——ALTER TABLE（最全能，连主键都能加）

SQL · 来源：11_索引优化体现.sql 
-- 给已有表加索引：与 create index 等价的另一种写法
alter table emp add index idx_emp_name (name);

-- 删除索引同样可以用 alter table
alter table emp drop index idx_emp_name;

同一语法还能写 ADD PRIMARY KEY (id)、ADD UNIQUE INDEX uk_phone (phone)、ADD INDEX idx_email (email(10))（前缀索引）、ADD INDEX idx_mix (a ASC, b DESC)（MySQL 8.0 降序索引），这是 CREATE INDEX 做不到的。

方式 3：给已有表加索引——CREATE INDEX（写法简洁，但注意：不能建主键！）

SQL · 来源：02_索引语法.sql 
-- 创建第一个索引：普通索引
create index idx_user_name on tb_user(name);

-- 创建唯一索引
create unique index uk_user_phone on tb_user(phone);

-- 创建联合索引（后面第 7 章的最左前缀都靠它演示）
create index idx_user_pro_age_sta on tb_user(profession,age,status);

-- 为 email 创建索引（本章演练最后会删掉，第 7 章改用前缀索引）
create index idx_user_email on tb_user(email);

三、删除、修改、重命名与隐藏索引

SQL · 来源：02_索引语法.sql / 11_索引优化体现.sql 
-- 删除索引（二选一，效果相同）
drop index idx_user_email on tb_user;

alter table emp drop index idx_emp_name;

MySQL 没有「直接修改索引包含的列」的语法，标准做法是先删旧索引、再建新索引。下面两条是脚本没有覆盖、但日常一定会用到的补充语法：

SQL · 补充语法（脚本未涉及，MySQL 5.7+ / 8.0） 
-- 重命名索引（MySQL 5.7+）
alter table tb_user rename index idx_user_name to idx_name;

-- 隐藏 / 恢复索引（MySQL 8.0）：不敢直接删时，先藏起来观察业务有无影响
alter table tb_user alter index idx_name invisible;
alter table tb_user alter index idx_name visible;

-- 删除带自增的主键前，必须先去自增
alter table tb_user modify id int not null;
alter table tb_user drop primary key;
⚠️ 经典报错避坑：删除带自增（AUTO_INCREMENT）的主键会失败！ MySQL 要求自增列必须有索引，直接删会报 Incorrect table definition。
两步解决：① 先用 MODIFY 去掉自增 alter table tb_user modify id int not null; → ② 再删主键 alter table tb_user drop primary key;

04

底层结构：为什么 MySQL 选择 B+ 树？

数据库的数据最终存在硬盘上，硬盘读写比内存慢得多。所以设计索引的核心目标很简单： 让树尽量“矮胖”（减少跳层读硬盘的次数），同时既能快速精确查找，又能快速查范围！

常见数据结构对比

数据结构 等值查询 范围查询 为什么 InnoDB 不选它（或选它）？
Hash 表 O(1) 极快 不支持 只适合 =，没法做 >、<、BETWEEN、排序和最左前缀匹配。
（注：InnoDB 内部自带“自适应哈希索引 AHI”作为高频等值查询的补充加速）
二叉树 / 红黑树 O(log₂N) 中序遍历 每个节点只有 2 个叉，几千万数据树高 20 多层，每次查都要读二十多次硬盘，太慢！
B 树（B-Tree） O(logₘN) 需回溯遍历 多叉矮树，但上层节点也塞了整行数据，占空间导致分叉变少、树变高；且最底层没连成链表，查范围费劲。
B+ 树（InnoDB 默认） 极稳 O(logₘN) 极快（链表） 完美方案：上层只放“路标”（键值 + 指针），所有真实数据都在最底层叶子节点，且叶子用双向链表手拉手连在一起！

🧮 算一笔超有意思的账：为什么 3 层 B+ 树能存 ~2000 万行数据？ InnoDB 每次从硬盘读写的基本单位叫数据页，默认大小是 16KB（16384 字节）：
  • 上层路标页（非叶子节点）：假设主键用 BIGINT（8 字节），InnoDB 指向下层页的指针占 6 字节，合计 14 字节一条路标。一页就能装 16384 ÷ 14 ≈ 1170 个叉！
  • 最底层数据页（叶子节点）：假设一行完整员工记录约占 1KB，一页能装 16 行数据。
  • 3 层总容量：第 1 层 1170 个叉 × 第 2 层 1170 个叉 × 第 3 层每页 16 行 ≈ 2190 万行！
    而且第 1 层根节点常驻内存（Buffer Pool），在 2000 万行里找一条记录只需 1~2 次磁盘 I/O，这就是 B+ 树快到飞起的原因！

性能分析三件套：执行频次 → 慢查询日志 → show profiles

在动手加索引之前，先要知道「表到底忙不忙、哪条 SQL 慢、慢在哪一步」。这三件套依次回答这三个问题，示例全部来自 03、04、05 三个脚本。

一、看执行频次：这张库到底在忙什么？

先看整体：查询多还是增删改多。如果以查询为主，索引优化的收益才大；如果写入占绝对大头，加索引反而会拖慢写入。

SQL · 来源：03_查看索引执行频次.sql 
-- session 看当前会话, global 看全局数据

-- 查看当前会话的 SQL 执行频次
show session status like 'Com_______';

-- 分开看增删改查各自执行了多少次
show global status like 'Com_select';
show global status like 'Com_insert';
show global status like 'Com_update';
show global status like 'Com_delete';

-- 查看 Innodb 引擎的行操作次数（了解即可）
show global status like 'Innodb_rows_%';
  • 'Com_______' 里是 7 个下划线，它是通配符：一次列出 Com_select、Com_insert、Com_update、Com_delete、Com_commit、Com_rollback 等所有以 Com_ 开头的命令计数。
  • Innodb_rows_read / inserted / updated / deleted 是行级计数，能看出「一条 SQL 实际碰了多少行」，比语句条数更接近真实压力。
  • global 与 session 的区别：global 是自数据库启动以来的累计值，session 只统计当前连接；排查业务整体状况看 global。

慢日志告诉你「这条 SQL 慢」，show profiles 进一步告诉你「慢在解析、发送数据还是排序」。它只对当前会话生效。

SQL · 来源：05_show_profiles.sql

-- 查看 profiling 是否开启，0 为关闭
select @@profiling;

-- 开启 profiling（只对当前会话生效）

-- 准备几条待分析的 SQL

四、三者的配合顺序

  1. 先看频次（03）：确认库以读为主、量级够大，值得优化。
  2. 再抓慢 SQL（04）：把 long_query_time 调到 1~2 秒甚至更低，拿到具体的慢语句和扫描行数。
  3. 最后看阶段（05）：对可疑 SQL 执行 show profiles + show profile for query，确认时间花在「Sending data」这类执行阶段。
  4. 接着交给 EXPLAIN（06）：看它到底走没走索引、扫了多少行，再决定加索引还是改 SQL。
✅ 记住这条排查链 执行频次 → 慢查询日志 → show profiles → EXPLAIN，从「哪里有问题」逐层收敛到「这一条 SQL 的哪一个执行步骤有问题」。

explain 怎么读：从 12 个字段到一条结论

在任意 SELECT 前加上 EXPLAIN，MySQL 并不会真的执行这条 SQL，而是把「打算怎么查」的执行计划打印出来：先读哪张表、用哪个索引、预计扫多少行、要不要额外排序。相当于给一条 SQL 拍了一张 CT 片，慢查询的病因九成都能从这张片子上看出来。

读法是有优先级的：先死盯 key → type → rows → Extra 这 4 个核心列，熟练之后再用 key_len、filtered、id 这些进阶列去解释「优化器为什么这么选」。

字段 重要度 通俗含义与排查方法
id 进阶 查询序号，一条 SQL 里每个 SELECT 分一个 id。
• id 相同：从上往下执行，排在上面的一般是驱动表
• id 不同：数字越大越先执行（子查询、UNION 分支）
• id 为 NULL：说明这一行是 UNION RESULT 这类临时结果集
select_type 进阶 这条 SELECT 的「身份」。SIMPLE 简单查询、PRIMARY 最外层、SUBQUERY 子查询、DERIVED 派生表（FROM 里的子查询）、UNION / UNION RESULT。
带 DEPENDENT 前缀表示子查询依赖外层，外层每行都要跑一遍子查询，是要重点盯的坏信号。
table 进阶 这一行正在访问哪张表。<derived2> 指 id=2 的派生表，<union1,2> 指 UNION 的合并结果，<subquery3> 指物化的子查询。
partitions 忽略 命中的分区名。没做分区表时恒为 NULL，日常可以直接无视。
type 必看 查询快慢等级。日常至少优化到 range，争取 ref，尽量消灭 ALL！
possible_keys 进阶 理论上“可能用到”的候选索引列表（有候选但 key 是 NULL 时，说明索引失效或被优化器放弃了）。
key 必看 MySQL 实际选用的索引名。如果是 NULL，说明没走索引！
key_len 进阶 实际用到的索引字节长度。超级实用：用它能精准算出联合索引到底命中了前几列！
（速算参考：INT 占 4 字节；允许 NULL 多加 1 字节；VARCHAR 变长多加 2 字节，utf8mb4 每字符占 4 字节）
ref 进阶 索引列在和谁比较：const（常量）、库名.表名.列名（连表时被驱动表拿主键/索引列去匹配）、func（函数结果）。
type 是 range 或 index 时它是 NULL，属于正常现象。
rows 必看 预估大概需要扫描多少行，越小越好。
注意它是估算值（来自采样统计），不是精确行数，会随统计信息变化。
filtered 进阶 按表上的条件过滤之后，剩余行数占 rows 的百分比。rows × filtered% ≈ 真正交给下一步的行数。
100.00 表示条件在索引层已经全部筛完；如果只有个位数（如 5%），说明索引只挡住了一点点，剩下的全靠 Server 层过滤，回表白跑很多次。
Extra 必看 附加信息，也是排查问题的第二现场。
• Using index：覆盖索引，不回表（极好）
• Using index condition：触发索引下推 ICP（很好）
• Using filesort：没利用索引排序，额外排了一遍（注意优化）
• Using temporary：建了临时表，常见于 GROUP BY（重点优化）

Extra 高频值速查（一眼分好坏）

Extra 取值 评级 含义与处理建议
Using index 好 覆盖索引：要查的字段索引里全都有，零回表，是梦寐以求的状态。
Using index condition 好 索引下推 ICP：在存储引擎里就用索引字段把不符合的行筛掉，减少回表次数。
Using index for group-by 好 GROUP BY / DISTINCT 直接借索引的有序性完成，连临时表都省了。
Using index for skip scan 好 8.0.13+ 的索引跳跃扫描：最左列没写、但它基数很低时，优化器自动拆成几段小范围扫描，比原先直接失效要聪明。
Using MRR 好 Multi-Range Read：先把待回表的主键排序再批量读，把随机 IO 尽量变成顺序 IO（需开启 optimizer_switch 里的 mrr）。
Using where 中性 Server 层还要再过滤一遍：条件里的列没进索引，只能回表取出整行后判断。它常和 Using index condition 同时出现。
Using filesort 注意 额外排了一遍序，ORDER BY 没吃到索引顺序。不是“用文件排序”，数据少时在内存里排，多了才落磁盘。
Using temporary 重点优化 建了内部临时表，常见于索引帮不上忙的 GROUP BY、DISTINCT、UNION，数据量大时又慢又占内存。
Using join buffer (hash join) 注意 8.0.18+ 被驱动表的连接列没索引，改用哈希连接（内存里建哈希表）。比老算法快，但给连接列建索引才是正解。
Using join buffer (Block Nested Loop) 注意 8.0.18 之前（或关闭 hash join 时）的块嵌套循环连接，同样说明被驱动表没走索引。
Select tables optimized away 好 只查 MIN() / MAX() / COUNT(*) 这类聚合时，优化器直接从索引头尾取值，压根不用扫表。
Impossible WHERE 中性 条件自相矛盾（如 id = 1 AND id = 2），优化器判定永远为空，连表都不扫，直接返回空结果。
No tables used 中性 查询里没有 FROM（或写的是 FROM DUAL），不需要访问任何表。
Distinct 好 找到第一条匹配的行就停止扫描，常用于 SELECT DISTINCT 且字段有索引的场景。
Start temporary / End temporary 注意 半连接（IN 子查询）被优化成“临时表去重”，用临时表来消除重复值。

id 与 select_type：先搞清谁先执行

单表查询的 id 永远是 1，看不出门道；一旦出现子查询、派生表、UNION，id 就是执行顺序的指纹。看个派生表的例子：

SQL · 派生表会先被物化成临时表 
EXPLAIN SELECT * FROM (
  SELECT profession, COUNT(*) AS c FROM tb_user GROUP BY profession
) t WHERE t.c > 2;
id select_type table type key Extra
1 PRIMARY <derived2> ALL NULL Using where
2 DERIVED tb_user index idx_user_pro_age_sta Using index; Using temporary

读法：id = 2 先跑（把 tb_user 按专业聚合成一张内部临时表），然后 id = 1 再查这张临时表——表名 <derived2> 里的 2 就是它的出生地。所以看到 DERIVED + Using temporary，就说明子查询被物化了，数据量大时优先改写成 JOIN。

🧠 四句口诀记住执行顺序 id 相同看上下（排上面的先读，通常是驱动表）；id 不同看大小（越大越先执行）；DERIVED 盯临时表（FROM 子查询会被物化）；DEPENDENT 盯执行次数（依赖外层的子查询会被反复执行）。

key_len 速算：联合索引到底用上了几列？

key_len 是唯一能直接读出“联合索引命中到第几列”的字段，比对着 SQL 猜靠谱得多。先把各类型的字节占用记住：

字段类型 key_len 占用 说明
整型 TINYINT 1 / SMALLINT 2 / INT 4 / BIGINT 8 定长，按类型宽度直接算
时间类型 DATE 3 / DATETIME 5 / TIMESTAMP 4 MySQL 5.6.4 起 DATETIME 由 8 字节优化为 5 字节
CHAR(n) n × 字符集字节数 utf8mb4 每字符 4 字节
VARCHAR(n) n × 4 + 2 多出的 2 字节用来记录实际长度
索引列允许 NULL 在以上基础上 + 1 多 1 字节标记该行是否为 NULL

套一遍联合索引的例子 实测对得上

索引 idx_user_pro_age_sta(profession VARCHAR(11), age TINYINT UNSIGNED, status CHAR(1))，三列都允许 NULL，utf8mb4：

  • 只用到 profession：11 × 4 + 2（变长）+ 1（NULL）= 47
  • 再命中 age：47 + 1 + 1 = 49
  • 三列全命中：49 + 4 + 1 = 54（status 是 CHAR(1)，utf8mb4 占 4 字节）
  • 反过来，如果 key_len 只有 47，就说明 age 和 status 都没参与索引定位

rows 与 filtered：优化器其实在「算账」

rows 和 filtered 都不是真实值，而是优化器拿着索引统计信息估出来的。filtered 越接近 100 越好——它表示索引已经帮你筛掉了多少行；如果 rows = 10000 而 filtered = 5，等于扫了一万行最后只剩五百行，中间那些回表全是白跑。

📊 估算不准怎么办？ rows 来自采样统计（默认只抽查 20 个数据页），大批量增删数据后可能严重失真，导致“明明有索引却不用”。此时执行 ANALYZE TABLE tb_user; 手动刷新统计信息，再重新 EXPLAIN。
另外，优化器算的成本 = IO 成本（读多少页）+ CPU 成本（比较多少行），所以它放弃索引不是犯傻，而是算出来走索引更贵（呼应第 9 章第 7 条）。

EXPLAIN 的 4 个进阶形态

EXPLAIN 日常首选

等价于 FORMAT=TRADITIONAL，输出就是上面那 12 列的表格，排查“走没走索引”够用了。

EXPLAIN FORMAT=JSON 看成本

会额外给出 cost_info（查询成本）、used_columns（真正用到的列）、attached_condition（下推到引擎的条件），想搞懂优化器为什么这么选就看它。

EXPLAIN FORMAT=TREE 8.0.16+

树形输出，一眼看清各步骤的嵌套与先后顺序，比横向表格更适合看多表连接。

EXPLAIN ANALYZE 8.0.18+

真的把 SQL 跑一遍，输出每一步的实际耗时 actual time、实际行数 rows、执行次数 loops，用来验证估算准不准。

终端输出 · EXPLAIN ANALYZE 会给出真实耗时 
mysql> EXPLAIN ANALYZE SELECT * FROM tb_user WHERE profession = '软件工程' \G
*************************** 1. row ***************************
EXPLAIN: -> Index lookup on tb_user using idx_user_pro_age_sta (profession='软件工程')
           (cost=1.75 rows=6) (actual time=0.043..0.061 rows=5 loops=1)
🛑 慎用 EXPLAIN ANALYZE 它会真实执行这条语句，对 UPDATE / DELETE 使用等于当场改数据。线上排查优先用普通 EXPLAIN 或 FORMAT=JSON；本地验证估算偏差时再用 ANALYZE，并且只跑只读查询。

实战判读顺序：30 秒定位一条慢 SQL

  1. key 是不是 NULL？是 → 完全没走索引，直接去第 9 章对号入座找失效原因。
  2. type 是不是 ALL / index？是 → 全量扫描，继续往下看 rows 的量级。
  3. rows 是否接近整表行数？是 → 索引区分度太低或统计信息过期（ANALYZE TABLE），考虑换索引列。
  4. key_len 是否用满了预期的列？没满 → 联合索引的最左前缀被范围查询截断，调整索引列顺序。
  5. filtered 是否很低？很低 → 索引只挡住了少量数据，剩下的都在 Server 层慢慢过滤。
  6. Extra 有没有 filesort / temporary / Using join buffer？有 → 分别对应排序、分组、连接三处额外开销。
  7. 前 6 步还说不清？看 FORMAT=JSON 的成本明细，或本机用 EXPLAIN ANALYZE 对比估算与实际。
✅ 一句话总结 一条 SQL 的性能问题，九成都能用四个问题问出来：key 走没走索引 → type 走得好不好 → rows 要扫多少行 → Extra 有没有额外开销。

索引怎么用才有效：回表、联合、最左前缀、前缀索引、ICP 与提示

1. 回表查询 vs 覆盖索引

结合第 2 章的「聚簇索引」和「二级索引」，这两个词一秒就能懂（示例来自 08_覆盖索引和回表查询.sql）：

  • 回表查询：执行 select * from tb_user where name = '吕布'; 时，先去 idx_user_name 找到 '吕布' 对应的主键 id = 1，但普通索引里没有性别、邮箱，所以还要拿着 id = 1 再跑一趟聚簇索引把整行取出来——查了两棵树！
  • 覆盖索引：执行 select id, name from tb_user where name = '吕布'; 时，你要的字段在 idx_user_name 叶子节点里全都有，直接返回，零回表！（Extra 显示 Using index）
图 2：回表查询 vs 覆盖索引流程图（开发中尽量避免随手写 SELECT * 的根本原因）
SQL · 来源：08_覆盖索引和回表查询.sql 
-- 覆盖索引：只查 name，索引叶子节点上就有 name 和主键 id
explain select id, name from tb_user where name = '吕布';

-- 多查一个 gender：gender 不在 name 索引上，必须回表取整行，Extra 里就没有 Using index
explain select id, name, gender from tb_user where name = '吕布';

-- 联合索引同理：带上 email 后索引不够用，只能回表
explain select profession, age, status, email from tb_user
where profession = '软件工程' and age = 23 and status = '1';

-- 如果经常按 name 查 email，可以建 (name, email) 联合索引，让这条 SQL 变成覆盖索引
create index idx_user_name_email on tb_user(name, email);
explain select name, email from tb_user where name = '吕布';

-- select * 一定会回表，这也是日常建议写明字段的原因
explain select * from tb_user where name = '吕布';

-- 演示结束后清理临时索引
drop index idx_user_name_email on tb_user;

2. 单列索引 vs 联合索引

多条件查询时，两个单列索引通常只能被优化器挑一个用，另一个条件要回表后到 Server 层再过滤；而联合索引能把多个条件都放进索引里完成。对比脚本：10_单列和联合索引.sql。

SQL · 来源：10_单列和联合索引.sql 
-- 为了演示，先给 age 和 status 各建一个单列索引
create index idx_user_age on tb_user(age);
create index idx_user_status on tb_user(status);

-- 两个条件分别命中两个单列索引：key 里只会显示一个，另一个靠回表后过滤
explain select * from tb_user where age = 23 and status = '1';

-- 范围条件时可能触发 index_merge（Extra 出现 Using union / Using intersect）
explain select * from tb_user where age > 20 and status = '1';

-- 删掉单列索引，换成一个联合索引 (age, status)
drop index idx_user_age on tb_user;
drop index idx_user_status on tb_user;
create index idx_user_age_sta on tb_user(age, status);

-- 同样的 SQL 走联合索引，key_len 更长，两个字段的过滤都在索引里完成
explain select * from tb_user where age = 23 and status = '1';

-- 只用到最左边的 age，索引依然生效
explain select * from tb_user where age = 23;

-- 只用到右边的 status，不满足最左前缀，索引失效
explain select * from tb_user where status = '1';

-- 演示结束后清理临时索引
drop index idx_user_age_sta on tb_user;

3. 联合索引的「最左前缀原则」

建联合索引 idx_user_pro_age_sta (profession, age, status) 时，B+ 树按「先按 profession 排 → 相同再按 age 排 → 再相同按 status 排」组织，就像按「省-市-区」排好的地址簿：

  • 查询条件必须从最左列 profession 开始，跳过它直接查 age/status 会全失效；有 profession 跳 age 查 status，则只有 profession 能定位。
  • where age = 23 and profession = '软件工程' 也能命中！MySQL 优化器会自动重排 AND 条件顺序。
  • 遇到严格范围查询 > / < 时，它右侧的列不能继续用于有序定位；但 >= / <= / BETWEEN / LIKE '软件%' 在边界相等区间上仍能利用右侧列。
SQL · 来源：06_exlain.sql（最左前缀法则） 
-- 三个字段全部命中，key_len 最长
explain select * from tb_user where profession = '软件工程' and age = 23 and status = '1';

-- 只用前两个字段，依然生效
explain select * from tb_user where profession = '软件工程' and age = 23;

-- 跳过最左边的 profession，索引失效
explain select * from tb_user where age = 23 and status = '1';

-- 跳过了中间的 age，只有 profession 生效
explain select * from tb_user where profession = '软件工程' and status = '1';

4. 前缀索引：长字符串怎么省空间

邮箱、URL 这类长字符串整列建索引太占空间，可以只取前 n 个字符。难点是 n 怎么定——靠区分度（不同值个数 / 总行数，越接近 1 越接近整列）。示例来自 09_前缀索引.sql。

SQL · 来源：09_前缀索引.sql 
-- 整列的区分度：不同值的个数 / 总行数，越接近 1 说明重复越少
select count(distinct email) / count(*) from tb_user;

-- 看前 5 个字符的区分度，明显比整列低
select count(distinct substring(email, 1, 5)) / count(*) from tb_user;

-- 看前 10 个字符的区分度，前缀越长越接近整列，但索引也越大
select count(distinct substring(email, 1, 10)) / count(*) from tb_user;

-- 用前 5 个字符建前缀索引
create index idx_user_email_5 on tb_user(email(5));

-- 建好后 Sub_part 显示 5，说明只对前 5 个字符建了索引
show index from tb_user;

-- 前缀索引只能定位到前缀，剩下的字符要回表比较，所以没有 Using index
explain select * from tb_user where email = 'lvbu666@163.com';

-- 也无法直接支持按整列 order by / group by
explain select email from tb_user order by email;

-- 演示结束后清理临时索引
drop index idx_user_email_5 on tb_user;
⚠️ 前缀索引的边界 前缀索引不能覆盖索引（Extra 不会出现 Using index），也不能支持整列的 ORDER BY / GROUP BY。区分度接近整列时才值得用，否则回表次数会变多，得不偿失。

5. 索引下推（ICP, Index Condition Pushdown）

MySQL 5.6 引入的默认优化，其实非常好理解！假设有联合索引 (profession, age, status)，查 select * from tb_user where profession = '软件工程' and age > 20 and status = '1';：

  • 老做法（无 ICP）：只用 profession 定位，把命中的行全部回表取整行，再逐行判断 age 和 status（大量白回表）。
  • 开启 ICP（默认）：age、status 本来就在索引树里，MySQL 直接在遍历索引时就用它们过滤，只把真正符合条件的记录拿去回表，大幅减少回表次数！（Extra 显示 Using index condition）
SQL · 来源：06_exlain.sql 
-- age 用了范围查询后，它右边的 status 不再参与定位，但仍能靠 ICP 过滤少回表
explain select * from tb_user where profession = '软件工程' and age > 20 and status = '1';

-- 业务允许时尽量用 >= / <=，右边的 status 还能继续参与索引定位
explain select * from tb_user where profession = '软件工程' and age >= 20 and status = '1';

6. SQL 提示：手动指挥优化器挑索引

优化器偶尔会挑错索引，可以在表名后加提示干预，只对当前这一条 SQL 生效。示例来自 07_SQL提示.sql。

SQL · 来源：07_SQL提示.sql 
-- 先确认 tb_user 上已有哪些索引，提示里写的索引名必须和这里一致
show index from tb_user;

-- 再给 profession 单独建一个索引，用来演示「同一字段有多个索引时优化器的选择」
create index idx_user_pro on tb_user(profession);

-- 不加任何提示：profession 上有两个索引，由优化器自己比较代价来挑
explain select * from tb_user where profession = '软件工程';

-- 建议使用联合索引
explain select * from tb_user use index(idx_user_pro_age_sta)
where profession = '软件工程';

-- 忽略联合索引，优化器只能退而使用 idx_user_pro
explain select * from tb_user ignore index(idx_user_pro_age_sta)
where profession = '软件工程';

-- 强制使用联合索引：即使全表扫描更便宜，也必须走这个索引
explain select * from tb_user force index(idx_user_pro_age_sta)
where profession = '软件工程';

-- force index 要谨慎：范围条件命中大量数据时，回表次数多，可能比全表扫描更慢
explain select * from tb_user force index(idx_user_pro_age_sta)
where profession > 'a';

-- 演示结束后清理临时索引
drop index idx_user_pro on tb_user;
✅ 三种提示的区别 USE INDEX 只是建议，优化器可以不听；IGNORE INDEX 让它别用某个索引；FORCE INDEX 是强制，用错了会慢得更彻底——加之前先看 explain 的 rows。

二、加索引前后的真实对比

同样一张表、同样一条查询，唯一变量就是「有没有索引」：

SQL · 来源：11_索引优化体现.sql 
-- 根据主键查询，很快，因为构建了索引
select * from emp where id =1000;
explain select * from emp where id =1000;

-- 根据姓名查询，此时没有构建索引，查询比主键慢得多
select * from emp where name='尤军';

-- 为姓名构建索引 (测试花费了 15 秒)
create index idx_emp_name on emp(name);
-- 另一个语法
-- alter table emp add index idx_emp_name (name);

-- 再根据名字查，此时 type 变成 ref
select * from emp where name='尤军';
explain select * from emp where name='尤军';

-- 没有加索引的 emp_no，type 还是 ALL
explain select * from emp where emp_no=100000006;

-- 删除索引
alter table emp drop index idx_emp_name;
-- drop index idx_emp_name on emp;

能读出的结论 正面

  • where id = 1000 走聚簇索引，type = const，rows = 1，几乎瞬间返回。
  • 给 name 建索引后，同一条 SQL 从 type = ALL 变成 type = ref，扫描行数骤降。
  • 建索引本身是有成本的：千万行数据上执行 create index 实测要 15 秒左右，线上大表要评估影响窗口。

埋着的暗坑 implicit cast

emp_no 是 VARCHAR(9)，脚本却写 emp_no = 100000006（数字）。

字符串列和数字比较会触发隐式类型转换，等价于在索引列上套函数，即使建了索引也会失效——正确写法是 emp_no = '100000006'。这条正好是第 9 章失效场景的活例子。

三、深分页 LIMIT 1000000, 10 怎么优化

在千万行的 emp 上执行 select * from emp order by id limit 1000000, 10;，MySQL 得先扫描并扔掉前面 100 万行（走二级索引还要先回表 100 万次），才给你最后 10 行，慢到卡死。两种立竿见影的解法：

SQL · 补充实战（脚本未涉及，基于 11 的 emp 表） 
-- 原始写法：扫 100 万行只为丢掉它们
select * from emp order by id limit 1000000, 10;

-- 方案 1（最快，推荐）：游标分页——记住上一页最后一条的 id，直接跳过前 100 万条
select * from emp where id > 1000000 order by id limit 10;

-- 方案 2（必须跳页时用）：延迟关联——先只查 10 个 id，再 JOIN 回表取完整行
select e.*
from emp e
inner join (
  select id from emp order by id limit 1000000, 10
) t on e.id = t.id;
-- 原理：子查询只查 id 触发覆盖索引，免去 100 万次回表，外层只回表 10 次！
📌 为什么 limit 越大越慢？ LIMIT offset, n 的 offset 不是「跳过」，而是先取出再丢弃。所以 offset 越深，白扫的行越多；只有把「定位」和「取数据」拆开（游标直接定位 / 延迟关联只取 id），才能把代价从 O(offset) 降到 O(n)。

索引失效场景、设计原则与自测

一、常见索引失效场景（例子取自 06_exlain.sql / 10_单列和联合索引.sql）

建了索引却没生效？对照下面 10 个场景一查一个准，每张卡片都是 tb_user 上的真实写法：

1. 对索引列做加减运算或套用函数 最高频
❌ where substring(phone, 10, 2) = '15'
❌ where year(createtime) = 2001
✅ where phone like '177999900%'
✅ where createtime >= '2001-01-01' and createtime < '2002-01-01'

记住口诀：把计算移到等号右边，保持索引列干干净净！（MySQL 8.0 支持显式建函数索引）

2. 字符串类型的索引列忘了加引号（隐式类型转换） 极易疏忽
❌ where phone = 17799990000 -- phone 是 varchar
✅ where phone = '17799990000'

底层原因：MySQL 比较字符串和数字时，会把字符串转数字，相当于在索引列上偷偷套了函数 CAST(phone AS SIGNED)！
反过来思考：如果 id 是整型，写 WHERE id = '10' 不会失效，因为转换发生在右边的常量 '10' 上，索引列没动。

3. LIKE 模糊查询以通配符 % 开头 高频
❌ where profession like '%工程'
✅ where profession like '软件%'

原因：字符串按从左到右顺序排，左边不确定就找不到起点。（大数据量前后模糊请用全文索引或 ES）

4. 联合索引违背最左前缀原则 高频
❌ idx_user_pro_age_sta → where age = 23 and status = '1'
✅ where profession = '软件工程' and age = 23 and status = '1'

原因：跳过了最左列 profession，无法从 B+ 树根节点逐层二分查找；只写 status = '1' 同样失效。

5. OR 连接了没有索引的列 常见
❌ where id = 1 or age = 23 -- age 无索引
✅ where id = 1 or name = '吕布'（两边都有索引）

原因：只要 OR 有一侧必须全表扫描，MySQL 就干脆直接全表扫一遍。

6. 联合索引中范围查询（> / <）截断后面的列 注意顺序
⚠️ where profession = '软件工程' and age > 20 and status = '1'
✅ 业务允许时改成 age >= 20，右侧 status 还能继续走索引

原因：age > 20 后 status 不再局部有序，无法参与定位（但可借 ICP 过滤减少回表）；>= 含等值边界，右侧列还能用。

7. 使用 !=、<>、NOT IN、IS NOT NULL（CBO 成本真相！） 进阶真相

很多入门资料说它们“绝对失效”，这不严谨！MySQL 内部有个基于成本的优化器（CBO）会自己算账。06_exlain.sql 里正好有一组现成对比：where phone >= '17799990000' 几乎命中全表，回表比全表扫还慢，优化器干脆放弃索引；而 where phone >= '17799990017' 只命中极少数行，索引照走不误。结论：失效与否取决于“命中比例”，不是运算符本身。

8. 连表查询时两表字符集 / 排序规则（Collation）不一致 实战暗坑

比如 A 表的 order_no 用 utf8mb4_general_ci，B 表用 utf8mb4_0900_ai_ci（MySQL 8.0 默认），两表 JOIN 时会偷偷触发编码转换，导致被驱动表索引失效！解决：全库统一字符集和排序规则。

9. ORDER BY 排序方向混用（触发 Using filesort） 排序优化
⚠️ INDEX(a, b) → ORDER BY a ASC, b DESC
✅ 同升同降 ORDER BY a ASC, b ASC（或 MySQL 8.0 建降序索引 INDEX(a ASC, b DESC)）

原因：普通联合索引两列都是升序的；同升（正扫）或同降（倒扫）都能免排序，一升一降就无法直接沿链表读出。

10. 表里数据太少，或者查询结果占比太大（做实验必看！） 新手别慌

自己建测试表只插了 3~5 条数据，或者查询条件命中全表一大半，优化器一算账发现直接全表扫更快，就会主动显示 type = ALL——06_exlain.sql 里 where phone >= '17799990000' 就是这种「数据分布导致不走索引」的典型，属于正常现象，不是索引坏了。

二、设计原则：什么时候该建、什么时候不该建？

✅ 推荐建索引的情况

  • 数据量较大（几万行以上）且查询频繁的表。
  • 高频出现在 WHERE、ORDER BY、GROUP BY、JOIN ... ON 的字段。
  • 区分度高（不重复值多）的列，如手机号、订单号、用户 ID。
  • 多条件查询优先建联合索引：遵循「等值放左、范围放右、高频与高区分度放左」，并消灭冗余索引（有了 (a, b) 就别再单建 (a)）。

❌ 不建议建索引的情况

  • 数据极少的表（几百行的小配置表）。
  • 重复度极高的列（如性别、是否删除 0/1）。
  • 会被频繁修改（UPDATE）的列。
  • 超大文本字段（TEXT / BLOB），超长字符串可考虑前缀索引。
  • 单表索引别建太多，一般控制在 5~6 个以内；索引列尽量设为 NOT NULL。

三、为什么主键推荐用自增整型（INT / BIGINT），而不是 UUID？ 经典高频

两大核心原因，一听就明白： 1. 减少页分裂：聚簇索引按主键顺序存数据。自增 ID 每次往最后一页末尾追加，满了直接新开一页，特别整齐；而 UUID 是乱序的，新数据经常硬挤进已满的中间页，触发页分裂和大量碎片。
2. 让所有二级索引更瘦小：前面讲过，每个二级索引叶子都要存主键值。BIGINT 才 8 字节，UUID 字符串高达 36 字节，主键小，整张表的所有二级索引体积都能小一大圈！

四、课后自测与打卡

例子都取自 06_exlain.sql 与 10_单列和联合索引.sql。点击「查看解析」核对答案，勾选「已掌握」会自动保存进度到浏览器本地。

基础 Q1：用 desc tb_user; 查看表结构时，Key 列的 PRI、UNI、MUL 分别是什么意思？
• PRI：主键索引（Primary Key）
• UNI：唯一索引（Unique Key）
• MUL：普通索引，或者联合索引的第一列（Multiple，允许值重复）
基础 Q2：删除带 AUTO_INCREMENT 自增属性的主键时直接报错了，正确操作是什么？
MySQL 要求自增列必须有索引，必须先去掉自增，再删主键：
1. ALTER TABLE 表名 MODIFY id INT NOT NULL;
2. ALTER TABLE 表名 DROP PRIMARY KEY;
基础 Q3：CREATE INDEX 和 ALTER TABLE ... ADD INDEX 有什么区别？想修改索引包含的列怎么改？
• 区别：CREATE INDEX 不能用来创建主键索引；而 ALTER TABLE 既能建主键，还能一次加多个索引，功能更全。
• 修改列：MySQL 没有直接修改索引列的命令，标准做法是先删除旧索引，再建新索引（如果只是改名，可用 ALTER TABLE 表名 RENAME INDEX 旧名 TO 新名）。
基础 Q4：为什么 WHERE phone = 13800138000（字符串列漏引号）会失效，而 WHERE id = '100'（整型列加引号）不失效？
MySQL 比较字符串和数字时，会把字符串转成数字：
• phone 是字符串列：转换发生在索引列本身（等价于套了函数），导致失效。
• id 是数字列：转换发生在右边的常量 '100'，索引列保持原样，照常走索引。
进阶 Q5：B+ 树相比 B 树强在哪三点？为什么 3 层 B+ 树就能装 2000 万行数据？
强在三点：① 非叶子节点只存路标不存整行数据，单页分叉多、树极矮、I/O 极少；② 叶子节点用双向链表串联，范围查询飞快；③ 每次都查到叶子，性能稳定。
2000 万估算：每页 16KB，非叶子页每条路标 14B 可放 ~1170 个指针，叶子页按每行 1KB 放 16 行，1170 × 1170 × 16 ≈ 2190 万行。
进阶 Q6：联合索引 idx_user_pro_age_sta(profession, age, status)，执行 WHERE profession = '软件工程' AND age > 20 AND status = '1' 时，status 完全没发挥作用吗？
status 确实无法用于索引定位（被开区间范围 age > 20 截断），但它并不是完全没用！在 MySQL 5.6+ 默认开启索引下推（ICP）的情况下，存储引擎会在遍历索引树时顺手用 status = '1' 过滤，避免把不符合的记录拿去回表。
进阶 Q7：什么是「回表」和「覆盖索引」？为什么说“主键越小，整张表的二级索引都越小”？
• 二级索引叶子只存“索引列 + 主键 id”。查其他列需要拿着 id 再去主键树查一遍，叫回表；要查的列全在二级索引里不用回表，叫覆盖索引。
• 因为每一个二级索引的每一条叶子记录都要冗余存一份主键值，所以主键（如 8B 自增 BIGINT vs 36B UUID）越小，所有二级索引就越紧凑。
进阶 Q8：10_单列和联合索引.sql 里给 age、status 各建一个单列索引，和建一个联合索引 (age, status)，查 WHERE age = 23 AND status = '1' 时差在哪？
1. 两个单列索引：key 通常只显示其中一个（如 idx_user_age），另一个条件要回表取整行后在 Server 层过滤；部分场景触发 index_merge，但合并本身也有开销。
2. 一个联合索引 (age, status)：key 显示 idx_user_age_sta，两个条件都在索引里完成，key_len 更长、回表更少。
3. 反过来只查 status = '1' 时，联合索引因不满足最左前缀而失效——这就是「联合索引列顺序」比「多建单列索引」更需要设计的原因。
