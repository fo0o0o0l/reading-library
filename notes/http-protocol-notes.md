# HTTP 协议笔记

> 这份笔记只讲" HTTP 是怎么一回事"，不写代码。看完之后，你应该能明白：浏览器敲一个网址回车，背后发生了什么；服务器返回的那些东西各是什么；以及为什么写 FastAPI 接口本质上就是在"接住 HTTP 请求、给出 HTTP 响应"。

---

## 一、先用一句话理解 HTTP

HTTP 是"浏览器（客户端）"和"服务器"之间约定好的一套**对话规矩**。

规矩的核心只有一条：

> **客户端先问一句，服务器再答一句。服务器从不主动开口。**

这个"一问一答"就叫**请求（Request）**和**响应（Response）**。HTTP 里所有复杂的东西，都是为了让这两句话说得清楚、不出错、还能被中间设备（缓存、代理）看懂。

---

## 二、为什么要有这套协议？

### 1. 因为两端互相不认识

浏览器是浏览器公司写的，服务器是你写的。如果双方没有共同约定，浏览器发过去一堆字节，服务器根本不知道哪一段是"我要访问哪个页面"，哪一段是"我的账号密码"。

于是大家约定：**发过去的第一个东西先说清楚"我要干什么"，后面再附上补充信息**。这就是请求行、请求头、请求体的由来。

### 2. 因为它要跨网络、跨很多台机器

一个请求从你的电脑到服务器，中间可能经过路由器、运营商、CDN、反向代理、负载均衡。这些设备并不关心你的业务逻辑，但它们需要看懂一些基本信息才能工作：这个请求能不能缓存？要不要压缩？是不是同一个人发的？

所以 HTTP 把信息分成了两类：

- **给人/给业务看的内容**：响应体里的网页、JSON 数据
- **给中间设备看的元信息**：请求头、响应头

这种"内容"和"说明书"分开的设计，是 HTTP 最重要的思路。理解了这一点，后面的东西都很自然。

### 3. 为什么是"无状态"

HTTP 每一问一答之间，服务器**默认不记得你上一次问过什么**。第一次请求和第二次请求，对服务器来说就像两个陌生人。

这不是偷懒，而是为了简单和可扩展：任何一台服务器都能处理任何一个请求，加机器就能扛更多流量，不需要同步"记忆"。

代价是"登录状态"这类需求没法天然实现，于是又补了 Cookie、Session、Token 这些机制，用"每次请求都带上一个小凭证"的方式，让无状态的协议看起来像有记忆。**这是理解登录原理的关键**。

## 三、一次请求长什么样

一次 HTTP 请求可以拆成三块，顺序固定：

### 1. 请求行：我要干什么

形如：`请求方法 + 资源路径 + 协议版本`

用文字描述就是：

> 用 GET 这个方法，去拿 `/book/3` 这个资源，使用 HTTP/1.1 版本。

为什么不把"方法"和"路径"合并成一个字符串？因为服务器需要**分开判断**：路径决定"找哪个处理逻辑"，方法决定"对这个资源做什么动作"。同一个路径，用 GET 是查看，用 DELETE 是删除，用 PUT 是替换。分开写，路由才好匹配。

### 2. 请求头：补充说明（键值对）

请求头是一行一行的"属性：值"，用来描述这次请求的附加信息。常见的几类：

- `Host`：你要访问的是哪个域名。一台服务器上可能挂很多网站，靠它区分。
- `User-Agent`：我是什么浏览器/什么系统。服务器可据此返回不同内容。
- `Accept`：我能接受什么格式的返回（比如我要 JSON 还是网页）。
- `Content-Type`：我这次发过去的正文是什么格式（比如表单、JSON）。
- `Authorization`：我用来证明"我是谁"的凭证，比如一段 Token。
- `Cookie`：浏览器替我保管、并自动带上的小纸条，服务器靠它认出你。
- `Content-Length`：正文有多长。服务器需要知道读到哪里为止。

为什么用键值对、而不是固定格式？因为协议要能不断加新能力。加一个新需求，只是多一个头，老服务器不认识就忽略它，不会崩。这是 HTTP 能活几十年的原因之一。

### 3. 请求体：真正要送过去的内容

不是每个请求都有。GET 一般没有（"我只是来拿东西，不给你送东西"），POST/PUT 通常有（提交表单、上传 JSON）。

请求体和请求头之间会空一行，这个空行很重要：它告诉服务器"补充说明到此结束，下面开始是正文"。协议里这种"用空行分隔"的做法，就是为了让接收方能明确知道边界。

## 四、一次响应长什么样

结构和请求对称，也是三块：

### 1. 状态行：结果怎么样

形如：`协议版本 + 状态码 + 一句短语`

> HTTP/1.1 200 OK

状态码是给**程序**看的，那句短语是给**人**看的。程序只认数字。

### 2. 响应头：这次返回的说明

常见的：

- `Content-Type`：返回的正文是什么（`text/html` 网页、`application/json` 数据、图片等）。
- `Content-Length`：正文长度。
- `Set-Cookie`：服务器让浏览器存一张小纸条，下次请求自动带上。这是"记住你"的起点。
- `Cache-Control` / `ETag` / `Last-Modified`：告诉浏览器"这内容能缓存多久""内容变了没有"。有了它，刷新页面不用每次都重新下载，省带宽也更快。
- `Location`：配合 3xx 状态码使用，意思是"你要的东西搬到这个新地址了"。

### 3. 响应体：真正的结果

网页的 HTML、接口的 JSON、一张图片的二进制。它和请求体一样，靠 Content-Type 说明格式，否则浏览器不知道该怎么解析——这就是为什么"返回一堆 JSON 但 Content-Type 写成 text/plain"时，前端会解析失败。

## 五、请求方法：为什么不止 GET 和 POST

很多人以为"拿数据用 GET，提交用 POST"就够了。那为什么标准里还有 PUT、PATCH、DELETE、HEAD、OPTIONS？

因为它们表达的是**不同的语义**，而语义带来实际好处：

- **GET**：查看资源，不应改变服务器状态。
- **POST**：新建资源 / 提交数据，通常每次执行都会产生新结果。
- **PUT**：整体替换某个资源。同样的内容发两次，结果一样。
- **PATCH**：局部修改某个资源。
- **DELETE**：删除资源。
- **HEAD**：只要响应头，不要正文。用来快速检查"这个文件在不在、有多大、变没变"，省流量。
- **OPTIONS**：问服务器"这个资源支持哪些方法"。浏览器的跨域预检请求（CORS）用的就是它。

这里有两个经常被提到的性质，理解了会觉得设计很合理：

- **安全（Safe）**：GET、HEAD 这类不该改动数据。所以浏览器敢预加载、敢缓存、爬虫敢随便爬。如果 GET 也能删数据，整个互联网的缓存和预取机制就没法工作了。
- **幂等（Idempotent）**：同一个请求做一次和做十次，服务器最终状态一样。GET、PUT、DELETE 是幂等的，POST 不是。所以网络抖动时，客户端可以放心重试 PUT/DELETE，但重试 POST 可能重复下单。

**一句话：方法不是"换个名字"，而是给中间设备和调用方一个"这个请求能不能缓存、能不能重试、会不会改数据"的承诺。**

## 六、状态码：为什么用数字分类

状态码是三位数字，第一位代表大类：

| 范围 | 含义 | 通俗解释 |
| --- | --- | --- |
| 1xx | 信息 | 还在处理，稍等 |
| 2xx | 成功 | 办好了 |
| 3xx | 重定向 | 不在这，去别处 |
| 4xx | 客户端错误 | 你请求得不对 |
| 5xx | 服务器错误 | 我这边出问题了 |

常见几个必须记住：

- **200 OK**：成功，正文就是结果。
- **201 Created**：创建成功，通常配合 Location 告诉你新资源在哪。
- **204 No Content**：成功但没正文，删东西常用。
- **301 / 302**：永久 / 临时跳转，浏览器会自动去新地址。
- **304 Not Modified**：你没变，我用本地缓存，不重新下载。
- **400 Bad Request**：请求格式有问题，服务器看不懂。
- **401 Unauthorized**：没登录 / 凭证无效。
- **403 Forbidden**：登录了，但没权限。
- **404 Not Found**：这个地址没有东西。
- **405 Method Not Allowed**：路径对，但方法不对（比如该用 POST 你用了 GET）。
- **422 Unprocessable Entity**：格式对，但内容不合法（FastAPI 的参数校验失败最常见这个）。
- **500 Internal Server Error**：服务器代码崩了。
- **502 / 503 / 504**：网关后面那台服务挂了 / 暂时不可用 / 超时。

为什么用"数字第一位分类"而不是一堆文字？因为程序要判断。客户端只要看第一位是 4 还是 5，就能决定"是我改请求"还是"等服务器恢复"。文字描述可以本地化、可以改，数字是稳定的接口。

## 七、HTTP 和 FastAPI 接口是什么关系

这是最该打通的一层。

**FastAPI 写的每一个接口，就是"某个方法 + 某个路径"的处理函数。**

比如你写了一个 `@app.get("/book/{id}")`，翻译成 HTTP 的话就是：

> 当有人用 **GET** 方法访问路径形如 `/book/3` 的地址时，由我来处理。

对应关系非常直接：

- 装饰器里的 `get` → HTTP 请求方法
- 装饰器里的 `"/book/{id}"` → 请求行里的路径；`{id}` 是占位符，实际值从路径里抠出来
- 函数的返回值 → 响应体
- FastAPI 自动设置的 `Content-Type: application/json` → 响应头
- 抛出的异常（比如参数不合法）→ FastAPI 自动转成 4xx 状态码和错误信息

换句话说，**框架不是另一套东西，它只是帮你把"读懂 HTTP 请求"和"组织 HTTP 响应"这两件重复又容易出错的事自动化了**。你只管写业务逻辑。

FastAPI 帮你做的事，逐条对回 HTTP：

1. **解析请求行**：从方法 + 路径找到该调用哪个函数（路由匹配）。路径不匹配返回 404，方法不匹配返回 405。
2. **解析请求头和请求体**：把路径参数、查询参数、JSON 正文取出来，转成 Python 类型。
3. **校验**：类型不对、长度超限，直接返回 422，并说明哪个字段错了。这正是状态码意义所在——让调用方明确知道"是请求的问题"。
4. **序列化响应**：把返回的字典/对象转成 JSON，并写好 Content-Type 和状态码。
5. **生成文档**：根据这些信息自动产出接口说明（Swagger 页面），本质上就是把"这个接口吃什么、吐什么"整理成人类可读的形式。

所以你在 FastAPI 里看到的 `Query`、`Path`、`Body`、`status_code`、`Header`、`Response`，都不是新概念，而是 HTTP 各部分的"编程入口"。

## 八、用一个文字例子走完整流程

假设你在浏览器访问一个查书的接口。

**第一步：浏览器发出请求（文字描述）**

> 请求行：用 GET 方法访问 `/book/3`，HTTP/1.1。
> 请求头：Host 是 `127.0.0.1:8000`；Accept 表示我期望 JSON；User-Agent 说明我是 Chrome；Cookie 里带上了之前登录的小纸条。
> 请求体：没有（GET 不送内容）。

**第二步：服务器处理**

> 框架先看路径 `/book/3` 有没有对应接口 → 有，是那个 `get_book` 函数。
> 再看方法是不是 GET → 是，匹配成功。
> 把路径里的 `3` 转成整数，传给函数。
> 函数查数据，返回结果。

**第三步：服务器返回响应（文字描述）**

> 状态行：HTTP/1.1 200 OK。
> 响应头：Content-Type 是 `application/json`；Content-Length 说明正文长度；Cache-Control 说明能缓存多久。
> 响应体：一段 JSON，比如书名、作者、简介。

**如果出错会怎样**

- 访问 `/book/abc`，而接口要求 id 是整数 → 返回 **422**，并说明 `id` 不是合法整数。
- 访问 `/books/3`（路径写错）→ 返回 **404**。
- 用 POST 访问 `/book/3`，但只定义了 GET → 返回 **405**。
- 函数里代码报错 → 返回 **500**。

你看，同一个路径，不同情况给出不同状态码，调用方（前端、爬虫、监控系统）就能做出不同反应。这就是为什么状态码必须准确，不能"什么都返回 200"。

## 九、几个容易混淆的点

**1. 路径参数、查询参数、请求体，都是"请求"的一部分**

- 路径参数：长在路径里的，如 `/book/3` 的 `3`，用于"定位资源"。
- 查询参数：问号后面的键值对，如 `?skip=0&limit=10`，用于"过滤、分页、排序"，不影响定位哪个资源。
- 请求体：正文，用于"提交一大坨数据"，比如新建一本书的全部字段。

为什么分开放？因为它们的职责不同：定位用路径，筛选用查询串，提交用正文。分清楚，接口才好用、好缓存、好调试。

**2. GET 也能带查询参数，但不该带正文**

GET 的语义是"取"，把参数放在 URL 里便于分享、收藏、缓存。正文在 GET 里没有明确语义，很多代理会直接丢掉，所以别依赖它。

**3. Cookie 是"浏览器替你自动出示"的，Token 是"每次自己出示"的**

它们解决的是同一个难题：HTTP 本身没有记忆，服务器怎么知道"你还是刚才那个人"？

- **Cookie 像一张寄存的小纸条**。服务器第一次回话时，顺手把写着标记的纸条塞给你（这就是响应里的 `Set-Cookie`），浏览器替你收好。之后你每次访问同一个网站，浏览器自动把纸条递过去，你完全不用操心。省事，但浏览器出于安全考虑，只肯对"存纸条的那个网站"出示它，别的网站来问一律不给——这就是常说的跨域限制。
- **Token 像一张随身携带的通行证**。服务器核对完身份，发给你一串字符。放在哪、什么时候带，由前端自己决定，通常是每次请求时亲手放进 `Authorization` 头里。浏览器不会自动帮你带，所以要多做一点保管和携带的事。

为什么会有两种？因为"保管人"不同。Cookie 交给浏览器保管，适合浏览器和服务器本来就是一家人的传统网页；Token 交给应用自己保管，适合前后端分开部署、手机 App 也要调用同一套接口的场景——手机上没有浏览器的 Cookie 那套机制，但发请求时带一个头，谁都能做到。

顺带说明：Session 不是第三种票据，它更像服务器的"登记本"。纸条上可能只写一个编号，真正的登录信息记在服务器本子上，服务器拿编号去查。这样纸条被人看到也没关系，因为上面没有真实身份。Token 则倾向于把身份信息（经过处理、看不出原样）直接写在证上，服务器自己检查一下就知道真假，不必翻本子，所以更容易靠增加机器来扛流量。

**4. 200 不代表业务成功**

HTTP 状态码描述的是"这次通信"的结果，不是你的业务结果。比如查一个不存在的用户，接口可能返回 200 + `{"code": 1001, "msg": "用户不存在"}`。这是业务层自定义的错误码，和 HTTP 层是两回事。好的设计是：**能用 HTTP 状态码表达的，就用 HTTP 状态码**（比如资源不存在就用 404），别让所有错误都挤在 200 里。

**5. HTTP 不负责"加密"**

HTTP 本身是明文，谁都能在路上看。HTTPS 就是 HTTP + TLS 加密，协议内容完全一样，只是套了一层保险。所以"HTTP 协议"和"HTTPS"在报文结构上没区别。

## 十、把它记成一句话

> **HTTP 就是"客户端用某个方法、访问某个路径、带上一些说明和数据，问服务器要东西；服务器用状态码说明结果，用头说明格式，用正文给出内容"的一问一答。**
>
> 方法回答"做什么"，状态码回答"结果如何"，头回答"怎么理解这份内容"，正文回答"内容是什么"。
>
> FastAPI 只是把这一问一答里重复的解析、校验、序列化工作替你做了，你写的每个路由函数，对应的是一个"方法 + 路径"的入口。
