0. 五分钟速览（核心结论 + 记忆锚点）

补充 · 本节要点

5 分钟版本：七条结论 + 七个锚点先背熟，细节留到后面按需回查。

一句话定义：传输控制协议（Transmission Control Protocol, TCP）是 TCP/IP 模型传输层的面向连接的、可靠的、基于字节流的传输协议，位于 IP 层之上、应用层之下。

七条核心结论

  1. 连接是"逻辑"的：双方各自维护一套状态（序列号、窗口、定时器），不存在物理链路。
  2. 建立连接三次握手、释放连接通常四次挥手：本质是"双方向的初始序列号同步"与"双方向的关闭通知"必须分别完成。
  3. 可靠的四件套：序列号（Sequence Number, seq）+ 确认（Acknowledgment, ACK）+ 超时重传 + 校验和（Checksum）。
  4. 字节流不是消息流：TCP 不保留应用层消息边界，"粘包/拆包"要由应用层自己解决。
  5. 两层"窗口"要分清：接收方给的 rwnd（接收窗口）与发送方算的 cwnd（拥塞窗口），实际可发 = min(rwnd, cwnd)。
  6. 流量控制防"压垮接收方"，拥塞控制防"压垮网络"，两者目标不同、机制独立。
  7. TCP 保证可靠、有序、不重复，但不保证实时：延迟抖动与队头阻塞（Head-of-Line Blocking, HOL）是它的结构性代价。

2. 协议定位与基本概念

补充 · 本节要点

TCP 解决的是“进程到进程”的可靠传输：端口定位进程，IP 负责逐跳转发。

协议栈位置：应用层（HTTP/FTP/SSH…） → 传输层：TCP / UDP → 网络层：IP → 链路层。

TCP 对上（应用层）提供进程到进程的通信能力（靠端口号区分进程），对下把数据交给 IP 层，由 IP 负责逐跳转发。

3. 四大核心特点

补充 · 本节要点

四大特点不是四个并列功能，而是同一套机制在不同侧面的表现。

3.1 面向连接（Connection-Oriented）

  • 通信前必须三次握手建立连接，通信结束后四次挥手（多数情况下）释放连接。
  • "连接"是逻辑连接：没有物理线路，只体现为两端各自维护的连接状态机（序列号、窗口、定时器、缓冲区）。
  • 一条 TCP 连接由四元组唯一确定：(源 IP, 源端口, 目的 IP, 目的端口)。

3.2 可靠传输（Reliable）

  • 确认机制（ACK）：接收方对已正确收到的数据回 ACK。
  • 超时重传：RTO 到期未收到 ACK 则重传。
  • 序列号：检测丢失、乱序、重复。
  • 校验和：检测传输过程中的比特错误。
  • 补充：还有快速重传（Fast Retransmit） 与 SACK 提升恢复效率（详见第 6 节）。

3.3 基于字节流（Byte-Stream）

  • TCP 把应用层数据视为无结构的字节序列，不保留消息边界。
  • 发送方有发送缓冲区，接收方有接收缓冲区；应用层的 write() 与网络上的分段是解耦的。
  • 由此产生两个常见现象：
    • 粘包：多次 send 的数据被合并到一个报文段；
    • 拆包：一次 send 的大数据被切成多个报文段。
    • 这类问题只能由应用层解决（定长、分隔符、长度字段，或改用带边界的协议）。
  • 与 UDP（User Datagram Protocol）的"报文边界保留"形成对照。

3.4 全双工（Full-Duplex）

  • 连接双方可同时发送与接收数据。
  • 两个方向各自独立维护序列号、窗口与定时器，因此关闭也是两个方向分别关闭 → 这正是"四次挥手"和"半关闭"的根源。

3.5 半关闭（Half-Close）——原稿未显式提到，但概念关键

  • FIN 的语义是"我这个方向没有数据要发了"，而不是"连接断了"。
  • 一方发出 FIN 后，仍可继续接收对方数据，这种状态称为半关闭（Half-Close）。
  • 编程接口：shutdown(fd, SHUT_WR) → 只关闭写方向并发送 FIN；close(fd) → 关闭整个描述符（全关闭）。
  • 常见双工协议（如 HTTP/1.0 短连接、FTP 数据连接）会先半关闭再等待对端结束。
校 正

校正：原稿"通信结束后通过四次挥手释放连接"表述可保留，但要注意：挥手次数取决于双方是否都有数据要发。若被动方已无数据可发，可将 ACK 与 FIN 合并成一个报文段，实际呈现为"三次挥手"；因此"必须是四次"是教学简化说法。

补充 · 记住这一点

全双工是四次挥手与半关闭的根源：两个方向各自独立关闭。

4. 三次握手（Three-Way Handshake）

补充 · 本节要点

三次握手的核心不是“打招呼”，而是双向同步 ISN 并协商参数；第三次 ACK 可以携带数据。

4.1 过程图（ASCII，所有 Markdown 阅读器均可显示）

ASCII 图示可横向滚动
        客户端 Client                              服务端 Server
             |                                           |
   CLOSED    |                                           |  LISTEN
             |                                           |
             |  ① SYN  seq=x                             |
   SYN_SENT  |  ---------------------------------------> |
             |                                           |  SYN_RCVD
             |  ② SYN+ACK  seq=y, ack=x+1                |
             |  <--------------------------------------- |
             |                                           |
             |  ③ ACK  seq=x+1, ack=y+1                  |
 ESTABLISHED |  ---------------------------------------> |  ESTABLISHED
             |                                           |

要点：

  • 第①步 SYN 消耗 1 个序列号，所以第②步回 ack = x + 1。
  • 第②步 SYN 同样消耗 1 个序列号，所以第③步回 ack = y + 1。
  • 第③步的 ACK 报文可以携带数据（这是唯一能"顺手带数据"的握手报文）。

4.2 状态迁移

阶段客户端服务端
初始CLOSEDLISTEN
发出 SYNSYN_SENT—
收到 SYN—SYN_RCVD
收到 SYN+ACKESTABLISHED（发出 ACK）—

4.3 为什么必须是三次？

  1. 同步双向初始序列号（ISN）：双方都需要知道"对方从哪个号开始"，且需要对方对自己 ISN 的确认。两次只能完成一个方向。
  2. 确认双向可达：客户端能确认"服务端能收、也能发"；服务端能确认"客户端能收、也能发"。
  3. 防止历史失效的连接请求：RFC 793 的经典理由——一个早已失效的重复 SYN 若到达服务端，两次握手会让服务端直接建立连接并空等，浪费资源；三次握手时客户端不会对该 SYN 回 ACK，连接建立不起来。
  4. 协商参数：MSS、窗口扩大因子（Window Scale）、SACK、时间戳（Timestamps）等选项都在 SYN 中交换，且只在 SYN 中协商，连接建立后无法再改。
说 明

因此"两次不够、四次多余"：三次是"双向同步 + 双向确认"的最小完备次数。

4.4 参数协商与安全细节

  • ISN 随机化：现代实现用随机/时钟驱动的 ISN，降低序列号预测攻击与旧连接干扰。RFC 6528 给出了基于 SipHash 的 ISN 生成算法。
  • SYN 队列：Linux 分 SYN queue（半连接队列，tcp_max_syn_backlog）与 accept queue（全连接队列，somaxconn）。SYN Flood 打满半连接队列，可用 SYN Cookie（tcp_syncookies）应对。
  • TCP Fast Open (TFO, RFC 7413)：允许在 SYN 中携带数据，省去一次 RTT；需双方支持且受安全策略限制。

5. 四次挥手（Four-Way Teardown）

补充 · 本节要点

挥手次数取决于双方是否还有数据要发：ACK 与 FIN 可合并时为三次，通常为四次。

5.1 过程图（ASCII）

ASCII 图示可横向滚动
   主动关闭方（如 Client）                    被动关闭方（如 Server）
        ESTABLISHED                                  ESTABLISHED
             |                                            |
             |  ① FIN  seq=u                              |
   FIN_WAIT_1|  ----------------------------------------> |  CLOSE_WAIT
             |  ② ACK  ack=u+1                            |
             |  <---------------------------------------- |
   FIN_WAIT_2|                                            |  应用继续发数据
             |                                            |  （半关闭：对端仍可发）
             |  ③ FIN  seq=w, ack=u+1                     |
             |  <---------------------------------------- |  LAST_ACK
             |  ④ ACK  ack=w+1                            |
             |  ----------------------------------------> |  CLOSED
   TIME_WAIT |   等待 2MSL 后 → CLOSED

要点：

  • FIN 也消耗 1 个序列号，所以对方回 ack = u + 1。
  • 第②步 ACK 与第③步 FIN 通常分开：因为 TCP 全双工，被动方的"我收到你要关"（ACK）与"我也发完了"（FIN）是两件独立的事。
  • 第③步的 seq 记为 w：被动方在此期间若发过数据，其序列号已推进。

5.2 状态迁移

阶段主动关闭方被动关闭方
发出 FINFIN_WAIT_1—
收到 FIN—CLOSE_WAIT
收到 ACKFIN_WAIT_2—
发出 FIN—LAST_ACK
收到 FINTIME_WAIT（回 ACK）—
收到 ACK—CLOSED
等满 2MSLCLOSED—
校 正

校正：TIME_WAIT 只出现在主动关闭方。 被动关闭方走 CLOSE_WAIT → LAST_ACK → CLOSED，不会进入 TIME_WAIT。大量 TIME_WAIT 说明本机是"主动关连接"的一方（常见于客户端/短连接服务器）；大量 CLOSE_WAIT 则说明本机应用没正确 close()，这是代码 BUG 而非内核参数问题。

5.3 TIME_WAIT 的两个作用

  1. 保证最后一个 ACK 能到达：若第④步 ACK 丢失，被动方会重传 FIN；主动方仍处于 TIME_WAIT，可再次回 ACK。若立刻关闭，对端重传的 FIN 只会收到 RST，导致对端异常关闭（可能出现数据截断）。
  2. 让旧连接的残余报文在网络中消散：等待 2MSL 确保本连接的"迷路报文"全部过期，避免被同一四元组的新连接误收（序列号虽随机，但仍有窗口重叠风险）。
校 正

校正：2MSL 的时长并非"固定 2 分钟"。 RFC 793 建议 MSL = 2 分钟（即 2MSL = 4 分钟），但 Linux 实现把 TIME_WAIT 固定为 60 秒（TCP_TIMEWAIT_LEN），与 RTO 无关；net.ipv4.tcp_fin_timeout 影响的是 FIN_WAIT_2 的停留时间，不是 TIME_WAIT。另外 TIME_WAIT 状态在高并发下可用 tcp_tw_reuse（仅对主动发起连接的客户端方向安全）缓解，但不建议 tcp_tw_recycle（已在 4.12+ 移除）。

5.4 为什么是四次不是三次？

  • 全双工：两个方向的关闭互不依赖。被动方收到 FIN 时，可能还有数据没发完，只能先 ACK 表示"我知道了"，等数据发完再 FIN。
  • 若被动方恰好也没有数据要发，ACK 与 FIN 可合并 → 形式上变成三次。所以"四次"是常见形态，不是协议强制次数。

6. 可靠传输与差错控制

补充 · 本节要点

可靠性 = 序号（定位）+ ACK（确认）+ 重传（补救）+ 校验和（查错），四者缺一不可。

TCP 的"可靠"由四组机制叠加实现。

6.1 序列号与确认号

  • 序列号是字节级编号（不是报文编号），seq = 本报文第一个数据字节的编号。
  • ack = 期望收到的下一个字节编号（累积确认，Cumulative ACK）。例：收到 1–1000 字节后回 ack=1001。
  • 因此 ACK 具有累积性：一个 ACK 等于确认了此前所有字节；乱序到达的字节不会推进 ACK。
  • 32 位序列号会回绕（wrap-around）；高带宽时延积（Bandwidth-Delay Product, BDP）链路上回绕更快，需靠时间戳选项做 PAWS（Protection Against Wrapped Sequences）判别。
校 正

校正：ACK 号不是"我已收到的最后一个字节"。 它是"我期望的下一个字节"，差 1 是经典错误点。

6.2 超时重传（RTO）

  • RTO 由 RTT 采样动态估算（Jacobson/Karels 算法）：SRTT（平滑 RTT）+ RTTVAR（偏差），并做上下界约束；Linux 下限常为 200 ms（TCP_RTO_MIN）。
  • Karn 算法：重传过的报文不做 RTT 采样（重传导致 ACK 归属歧义）；配合时间戳选项可放宽。
  • 指数退避（Exponential Backoff）：连续超时按 1、2、4、8… 倍增 RTO，避免拥塞时继续猛发。
  • 重传的两种触发：
    • 超时重传：RTO 到期（网络严重丢包/ACK 全丢）；
    • 快速重传（Fast Retransmit）：收到重复 ACK 达到阈值时立即重传，不等超时。

6.3 快速重传与 SACK

  • 触发条件：收到 3 个重复 ACK（Duplicate ACK，即同一 ack 号累计出现 4 次）时，认为该报文丢失，立即重传（阈值 dupthresh 可调，Linux 有 tcp_reordering）。
  • SACK（Selective ACK，RFC 2018）：在选项中标明"我已收到哪些块"，发送方可精确重传缺失部分，避免"go-back-N"式的重复发送。配套 DSACK 用于识别重复报文。
  • RACK / TLP（Linux 现代实现）：基于时间而非 ACK 计数判断丢包，对"每窗口丢包数少"的场景更准。

6.4 校验和（Checksum）

  • 16 位反码求和，覆盖 伪首部（Pseudo-Header）+ TCP 首部 + 数据 + 填充。
  • 伪首部含源/目的 IP，因此重算校验和必须知道 IP 层信息（NAT 改写地址时需同步更新）。
  • 只能检测错误，不能纠正；检测到错误直接丢弃，由重传补救。
校 正

校正：TCP 校验和在 IPv4 与 IPv6 下都是必需的。 （IPv6 中"校验和可选"的说法只适用于 UDP，见 RFC 8200。）另注意：校验和无法防御恶意篡改，安全需靠 TLS/IPsec。

6.5 可靠性 ≠ 实时性

TCP 保证的是"最终正确、有序、不重复"，为此会等待与重传，代价是延迟可能突增（如尾部丢包导致等待）。这正是实时业务转向 UDP/QUIC 的原因。

补充 · 记住这一点

ack 是“期望的下一个字节”，不是“已收到的最后一个字节”。

7. 流量控制（Flow Control）

补充 · 本节要点

流量控制是接收方对发送方的“限速通知”，靠 rwnd 与滑动窗口实现，零窗口时必须探测。

7.1 滑动窗口机制

接收方在每个 ACK 中携带窗口字段（rwnd），声明"从当前 ack 号起还能再收多少字节"，发送方据此限制在途数据量。

ASCII 图示可横向滚动
发送方视角（滑动窗口）:

   已发送且已确认   |   已发送未确认   |   可发送（窗口内）  |  不可发送
  -----------------|-----------------|-------------------|------------
                   ^                 ^                   ^
              send_una          send_next        send_una + rwnd
  • 收到 ACK 且窗口不变 → 窗口右移（滑动）。
  • 窗口变小 → 右边界左移（窗口收缩，RFC 建议尽量避免）。

7.2 零窗口与窗口探测

  • rwnd = 0 时，发送方暂停发送新数据，但不能就此静默：需启动持续定时器（Persist Timer），周期性发送零窗口探测（Zero Window Probe），接收方窗口恢复后回一个带非零窗口的 ACK。
  • 探测报文本身不算"新数据"，避免死锁（若双方都在等对方先动，就会互锁）。
校 正

校正：原文"窗口为 0 时发送方停止发送"需要补一句—— 停止的是新数据，探测报文与已发出的重传仍会继续。

7.3 窗口扩大选项（Window Scale, RFC 7323）

  • 首部窗口字段只有 16 位 → 最大 65535 字节，对高 BDP 链路远远不够。
  • 窗口扩大选项给出一个移位因子（0–14），实际窗口 = 字段值 × 2^factor，理论上限约 2^30 字节（1 GiB）。
  • 只能在 SYN 中协商，且因子对两个方向各自生效；一旦协商，连接期内不可改。

7.4 糊涂窗口综合症（Silly Window Syndrome, SWS）

  • 接收方每次只腾出很小空间就通告小窗口，或发送方只发很小数据 → 大量小报文，效率极低。
  • 对策：接收方延迟通告直到窗口够大（或达到半个缓冲区）；发送方用 Nagle 算法合并小数据（注意与延迟 ACK 组合可能引入 40 ms 级延迟）。
补充 · 记住这一点

rwnd 来自接收方，cwnd 由发送方推算，实际可发 = min(rwnd, cwnd)。

补充 · 一张图记住

8. 拥塞控制（Congestion Control）

补充 · 本节要点

拥塞控制是发送方对网络的“试探”：慢启动指数探路，拥塞避免线性增长，丢包后减半回退。

目标与流量控制不同：流量控制防压垮接收端，拥塞控制防压垮网络。

8.3 关于初始拥塞窗口（重要校正）

校 正

校正：原文"拥塞窗口从 1 个 MSS 开始"是历史描述，不是现行标准。

  • RFC 5681 允许初始窗口 IW = min(4*SMSS, max(2*SMSS, 4380 字节))，即最多 4 个 MSS；
  • RFC 6928 将其提升为 10 个 MSS（约 14600 字节），已成为主流实现默认值（Linux 3.0+）；
  • 且现代实现的第一步通常是"分批发（pacing / initial burst 限制）"，避免一次性突发丢包（RFC 7661 等）。

同时，ssthresh 的初始值不是固定常数：RFC 5681 建议"初始设为任意大的值"，具体实现各不同。

8.4 现代算法

算法思路特点
Reno / NewRenoLoss-based，AIMD经典教科书模型，高 BDP 下恢复慢
CUBIC（RFC 9438）以时间为自变量的三次函数增长Linux 默认，与 RTT 弱相关，高速链路表现好
BBR（Bottleneck Bandwidth and RTT）模型驱动，测量瓶颈带宽与最小 RTT不以丢包为信号，在丢包率高的链路上吞吐更稳；公平性仍有争议
Vegas / Veno以 RTT 延迟增长为信号更早退让，适合低缓冲网络
校 正

校正：原文"拥塞控制偏保守，在高延迟高丢包网络中吞吐可能受限"——方向正确但过于笼统。 该结论主要针对传统 loss-based（Reno 类）算法；CUBIC 已显著改善高 BDP 场景，BBR 在高丢包链路上表现更好。当前瓶颈更多来自算法选择与参数配置，而非 TCP 协议本身。

补充 · 记住这一点

慢启动其实不慢（指数增长）；初始窗口已是 10 MSS（RFC 6928），不是 1 MSS。

10. 与 UDP 的对比

补充 · 本节要点

TCP 用开销换可靠，UDP 用放弃保证换低延迟；QUIC 把可靠性做进用户态并绕开 TCP 队头阻塞。

维度TCPUDP
连接面向连接，需三次握手无连接，直接发
可靠性确认 + 重传，保证可靠有序不重复不保证；丢包、乱序、重复都可能
传输方式字节流（无消息边界）报文（保留边界，Datagram）
首部开销20–60 字节固定 8 字节
流量控制有（滑动窗口 rwnd）无
拥塞控制有（cwnd / CUBIC / BBR 等）无（由应用自行处理）
广播/组播不支持支持
传输效率建立/维护有开销，长连接效率高开销小，适合短交互
典型应用HTTP/HTTPS、FTP、SMTP、SSH、数据库连接DNS、DHCP、SNMP、VoIP、视频流、游戏、QUIC 底座

记忆：TCP 用"确认 + 重传 + 窗口"换可靠；UDP 用"什么都不管"换低延迟与自由。

补充：QUIC（HTTP/3 的传输层）在 UDP 之上重造了可靠传输、拥塞控制与多路复用，但把"连接"做进用户态并消除了 TCP 层的队头阻塞 —— 是现代演进方向。

补充 · 记住这一点

要可靠有序选 TCP；要低延迟、可容忍丢包或组播选 UDP；两者都要就看 QUIC。

11. 适用场景与局限

补充 · 本节要点

判断该不该用 TCP，只需问两件事：能否容忍建连与重传的延迟，是否需要绝对正确与顺序。

11.1 适合的场景

  • Web：HTTP/1.1、HTTP/2（TCP 承载）、HTTPS（TLS over TCP）。
  • 文件与邮件：FTP、SFTP、SMTP、IMAP/POP3 —— 需要完整性。
  • 远程登录与管理：SSH、Telnet（不推荐）、RDP（走 TCP）。
  • 数据库与中间件：MySQL、PostgreSQL、Redis（长连接，请求-响应）。
  • RPC / 服务间调用：gRPC（HTTP/2 over TCP）。
  • 共性：能容忍一定延迟、但对正确性与顺序敏感。

11.2 局限

  • 建连开销：三次握手至少 1 个 RTT（TFO 可省）。
  • 队头阻塞（HOL）：一个报文段丢失，后续已到达的数据也不能交付应用；HTTP/2 的多路复用仍受 TCP 层 HOL 制约（HTTP/3 用 QUIC 解决）。
  • 拥塞控制策略差异：loss-based 算法在高丢包链路吞吐受限；跨运营商/长肥管道（Long Fat Network, LFN）对窗口与算法很敏感。
  • 不保证实时性：重传与排队带来延迟抖动（Jitter），不适合强实时。
  • 状态开销：每连接占用内核内存与四元组，海量短连接会耗尽端口与 TIME_WAIT。
校 正

校正：原文"不适合短连接高频交互"需补充现代缓解手段。 现在常用：连接池/长连接（HTTP keep-alive）、TCP Fast Open、以及 HTTP/2 多路复用（减少连接数但不消除 TCP 层 HOL）。"不适合"是相对结论，不是绝对禁令。

11.3 什么时候换 UDP / QUIC

  • 实时音视频、实时游戏、直播：能容忍少量丢包，追求低延迟 → UDP（或 QUIC）。
  • 需要自定义重传/拥塞策略（如自研可靠传输）→ 基于 UDP 实现。
  • 需要穿透 NAT/防火墙且免握手 → QUIC（基于 UDP，但自带加密与拥塞控制）。
补充 · 记住这一点

“不适合短连接”是相对结论：连接池、keep-alive、TFO 都能缓解。

12. 常见易错点与面试高频问法

补充 · 本节要点

这一节把前面的机制“反着问”：每个易错点背后，都是一条被记反了的定义。

12.1 十个高频易错点

  1. ACK 号含义错位：ack 是"期望的下一个字节"，不是"已收到的最后一个字节"。
  2. 把 SYN/FIN 当成"不占序号"：它们各消耗 1 个序列号，+1 关系由此而来。
  3. 认为 TIME_WAIT 双方都有：只有主动关闭方进入 TIME_WAIT。
  4. 把 TIME_WAIT 与 CLOSE_WAIT 混为一谈：CLOSE_WAIT 是应用没关（代码问题），TIME_WAIT 是正常等待（协议行为）。
  5. 认为挥手必须四次：被动方无数据时 ACK+FIN 可合并，实际可能是三次。
  6. 把 FIN 理解为"连接断开"：FIN 只是半关闭的发送方向。
  7. 把 rwnd 和 cwnd 当成一回事：发送上限 = min(rwnd, cwnd)。
  8. "慢启动从 1 MSS 开始"：已过时，现代初始窗口为 10 MSS（RFC 6928）。
  9. "窗口字段 16 位所以最大 65535"：忽略窗口扩大选项，实际可达约 1 GiB。
  10. "TCP 保证不丢但不保证不重复/有序"：错，TCP 保证有序、去重、可靠交付（应用层看到的数据是完整的）。

12.2 面试高频问法（含答题骨架）

问题答题骨架（3 句话内）
为什么三次握手不是两次？双向 ISN 同步 + 双向可达确认 + 防历史失效 SYN；两次无法完成双向同步。
为什么四次挥手？全双工两个方向独立关闭；被动方可能还有数据，ACK 与 FIN 只能分开。
TIME_WAIT 的作用？保证最后 ACK 可达（对端重传 FIN 能应答）+ 让旧报文消散，避免端口复用串扰。
大量 TIME_WAIT 怎么办？先判断是否正常（主动关闭方多）；tcp_tw_reuse（客户端方向安全）、缩短 keep-alive、用长连接/连接池。
大量 CLOSE_WAIT 怎么办？应用未 close，查代码（连接泄漏、异常分支未关闭）。
粘包怎么解决？TCP 是字节流无边界；应用层定长/分隔符/长度字段，或换用带边界的协议。
如何区分流量控制与拥塞控制？前者防接收端溢出（rwnd，接收方通告），后者防网络过载（cwnd，发送方推断）。
快重传与快恢复区别？快重传是"立即重传丢包"，快恢复是"重传后不回到慢启动，cwnd 减半继续线性增长"。
长肥管道为什么慢？窗口不足 + RTT 大 → 需窗口扩大、合适的拥塞算法（CUBIC/BBR）、更大的缓冲。
TCP 与 UDP 如何选？要可靠有序 → TCP；要低延迟/可容忍丢包/组播 → UDP；折中看 QUIC。

14. 自测题（10 题）

说 明

先不看答案，用纸笔写关键数字与状态名。答案在第 15 节。

  1. 三次握手中，客户端发出 SYN(seq=x)，服务端回 SYN+ACK(seq=y, ack=?)，客户端再回 ACK(ack=?)。请填空，并说明 SYN 为什么要占一个序列号。
  2. 从"双向 ISN 同步"角度解释：为什么两次握手不够、四次握手多余？
  3. 四次挥手中，为什么 ACK 与 FIN 通常分开发送？什么情况下会退化为三次？
  4. TIME_WAIT 出现在哪一方？它的两个作用是什么？Linux 上它的实际时长是多少？tcp_fin_timeout 影响的是哪个状态？
  5. 什么是半关闭（Half-Close）？在 Socket 编程里如何实现半关闭？它和 close() 有什么区别？
  6. 接收方收到序号 1–1000 的数据后，应回 ack 等于多少？收到 1–1000、2001–3000（中间缺失）时会回什么？为什么？
  7. 发送方同时有 rwnd = 8000、cwnd = 3000（单位字节），此刻最多能发多少字节未确认数据？为什么要取小？
  8. 快重传的触发条件是什么？快恢复之后 cwnd 与 ssthresh 如何设置（RFC 5681 口径）？TCP 超时又会如何改变它们？
  9. 接收窗口通告为 0 后，发送方是否可以完全静默？若不能，靠什么机制恢复？
  10. TCP 首部最小/最大长度分别是多少？4 位数据偏移为什么最大只能表示 60 字节？窗口扩大选项能把窗口放大到什么量级？

15. 参考答案

  1. ack = x+1；ack = y+1。SYN 是"同步序列号"的报文，它本身要占一个序号位置，以便与后续数据字节的编号连续、并让对方的确认有明确指向（SYN 与 FIN 都属于"消耗序列号的控制报文"）。
  2. 两次握手只能完成单向的 ISN 同步（服务端知道了客户端的 ISN，客户端仍无法确认服务端是否收到自己的 ISN、也不知道服务端的 ISN 是否被正确确认）；三次握手实现"双向同步 + 双向可达确认"；四次没有额外信息可交换——第三个 ACK 已同时完成"确认对端 SYN"和"自己的参数已被接收"。
  3. 因为 TCP 是全双工：被动方收到 FIN 只代表"对端不再发送"，自己可能还有数据在发，所以只能先 ACK；数据发完才发 FIN。若被动方当时已无数据可发，且无需等待应用处理，则 ACK 与 FIN 可合并为一个报文段，表现为三次挥手。
  4. 只出现在主动关闭方（先发 FIN 的一方）。作用：① 若最后 ACK 丢失，对端重传 FIN 时还能应答，避免对端收到 RST 而异常关闭；② 等待 2MSL 让本连接的残余报文在网络中消散，防止相同四元组的新连接误收旧报文。Linux 实际为固定 60 秒（与 RTO 无关）。net.ipv4.tcp_fin_timeout 影响 FIN_WAIT_2 的停留时间，不是 TIME_WAIT。
  5. 半关闭指一方关闭发送方向（发 FIN）但仍可继续接收对端数据的状态（状态机上表现为主动方 FIN_WAIT_2、被动方 CLOSE_WAIT）。实现：shutdown(fd, SHUT_WR)。close() 是关闭整个描述符（两个方向，且释放 fd），shutdown 只影响数据流方向、不释放描述符。
  6. 正常应回 ack = 1001（期望下一个字节）。若只收到 1–1000 与 2001–3000（中间空洞），累积确认仍回 ack = 1001（除非启用 SACK，在选项里告知已收到 2001–3000 块）；因为累积 ACK 只推进到"连续收到的最后一个字节之后"。
  7. 最多 3000 字节。rwnd 是接收端能力上限，cwnd 是发送方对网络容量的推断，实际在途数据必须同时满足两者 → 取 min。
  8. 触发条件：收到 3 个重复 ACK（同一 ack 号累计出现 4 次，阈值 dupthresh 可调）。快恢复（RFC 5681）：ssthresh = max(FlightSize/2, 2*MSS)，cwnd = ssthresh (+3 MSS)，随后进入拥塞避免（线性增长）。若发生 RTO 超时：ssthresh = cwnd/2，cwnd 重置为 1 MSS（现代实现按 RFC 6928 的 IW 也可能重启为更大初值，但标准模型按 1 MSS），重新进入慢启动。
  9. 不能静默。发送方启动持续定时器（Persist Timer），周期性发送零窗口探测（Zero Window Probe）；接收方窗口恢复后回一个带非零窗口的 ACK，发送方据此恢复发送。
  10. 最小 20 字节、最大 60 字节。4 位数据偏移以 4 字节为单位（值 5–15），15×4 = 60。窗口扩大因子最大 14，65535 × 2^14 ≈ 2^30 字节（约 1 GiB）。

16. 动手验证：常用命令

补充 · 本节要点

命令的价值在于验证：先看状态分布，再抓一次握手，最后核对内核参数。

说 明

概念记住后，用这几条命令验证最有效。命令以 Linux 为例，Windows 可用 WSL 或对应工具。

查看连接与状态

Bash
# 查看 TCP 连接状态汇总
ss -s

# 查看 TCP 连接及定时器、窗口、拥塞信息
ss -ti

# 统计各状态数量（TIME_WAIT / CLOSE_WAIT 排查）
ss -tan | awk '{print $1}' | sort | uniq -c | sort -rn

抓包观察握手/挥手

Bash
# 只抓某端口上的 SYN/FIN/ACK 交互
tcpdump -i any -n 'tcp port 80 and (tcp[tcpflags] & (tcp-syn|tcp-fin|tcp-ack) != 0)'

关键内核参数

Bash
sysctl net.ipv4.tcp_syncookies      # SYN Cookie 开关
sysctl net.ipv4.tcp_max_syn_backlog # 半连接队列上限
sysctl net.core.somaxconn           # 全连接队列上限
sysctl net.ipv4.tcp_fin_timeout     # FIN_WAIT_2 超时（不是 TIME_WAIT）
sysctl net.ipv4.tcp_congestion_control  # 当前拥塞算法（cubic / bbr）
补充 · 记住这一点

大量 TIME_WAIT 先看是不是本机主动关闭；大量 CLOSE_WAIT 直接去查代码。

补充 · 排查清单（Linux）
  1. 看状态分布：ss -tan | awk '{print $1}' | sort | uniq -c | sort -rn。TIME_WAIT 多说明本机主动关闭多；CLOSE_WAIT 多说明应用没 close。
  2. 看监听队列：ss -lnt。监听套接字的 Recv-Q 是当前全连接队列长度，Send-Q 是 backlog 上限；Recv-Q 长期贴近 Send-Q 说明 accept 跟不上。
  3. 抓握手：tcpdump -n -i any 'tcp[tcpflags] & tcp-syn != 0'，确认 SYN → SYN+ACK → ACK 三步齐全、seq/ack 满足 +1 关系。
  4. 核对参数：sysctl net.ipv4.tcp_congestion_control net.core.somaxconn net.ipv4.tcp_max_syn_backlog。

以上命令与字段含义以 Linux 为准；其他系统命令不同，观察目标一致。

17. 校正记录（与原稿差异）

补充 · 本节要点

这一节是全文的“新旧说法对照”，面试失分往往就发生在这里。

按"以 RFC 与主流实现为准、不确定不写死"的原则，对原稿做了以下修正或补充：

#原稿表述校正后
1以 RFC 793 为基准RFC 793 已被 RFC 9293（2022） 取代，字段与控制位定义以 9293 为准
2慢启动"拥塞窗口从 1 个 MSS 开始"历史描述；RFC 5681 允许 IW ≤ 4 MSS，RFC 6928 提升为 10 MSS，为主流默认
3未说明初始 ssthresh初始值非固定常数，RFC 5681 建议"任意大"，实现各异
4"TIME_WAIT 等待 2MSL"（未点明归属）仅主动关闭方进入 TIME_WAIT；Linux 实际固定 60 s，tcp_fin_timeout 管 FIN_WAIT_2
5"通信结束后通过四次挥手释放连接"四次是常见形态；被动方无数据时 ACK 与 FIN 可合并，呈三次
6FIN 视为关闭连接FIN 只关闭发送方向，引出"半关闭（Half-Close）"与 shutdown(SHUT_WR)
7"确认机制（ACK）"补充：ACK 为累积确认，含义是"期望的下一个字节"，并普遍启用延迟确认
8快重传"收到 3 个重复 ACK"更精确：同一 ack 号累计 4 次（3 个重复 ACK），阈值 dupthresh 可调；补 RACK/TLP
9窗口为 0"发送方停止发送"停止的是新数据；仍需零窗口探测 + 持续定时器
10"TCP 头部固定 20 字节"最小 20 字节、最大 60 字节（数据偏移 4 位、单位 4 字节）
11标志位列举"SYN、ACK、FIN、RST、PSH、URG 等"RFC 9293 共 8 位，含 ECE/CWR（ECN）；NS 位已废弃（RFC 8311）
12校验和描述笼统补：覆盖伪首部；IPv4/IPv6 下 TCP 校验和均为必需（IPv6 中可选仅指 UDP）
13"序列号检测丢失和乱序"补：32 位序号会回绕，高 BDP 链路需时间戳做 PAWS；SACK 用于精确重传
14"拥塞控制偏保守，高延迟高丢包下吞吐受限"该结论主要针对 loss-based 算法；CUBIC（Linux 默认）/ BBR 已明显改善
15"不适合短连接高频交互"补充缓解手段：keep-alive、连接池、TFO（RFC 7413）、HTTP/2 多路复用（但 TCP 层 HOL 仍在）
16三次握手目的"确认双方收发能力"核心是双向 ISN 同步 + 参数协商（MSS/窗口扩大/SACK/时间戳），确认可达是附带结论
17未提 MSS 默认值未协商时默认 536 字节；MSS 取双方通告的较小值；MSS = MTU − 40

遇到底层细节，先查 RFC 编号与实现版本，再下结论。

延伸 · 5 题自测（点击显示答案）

先合上笔记自己回答，再点开对照；答案默认隐藏，打印时会自动展开。

1. 主动关闭方在收到对端的 FIN 之后进入哪个状态？要等多久？

进入 TIME_WAIT，回最后一个 ACK，等待 2MSL 后关闭。Linux 实现把该时长固定为 60 秒（与 RTO 无关）。

2. 接收方收到 1–1000 与 2001–3000 两段数据（中间有空洞），未启用 SACK 时回的 ack 是多少？

ack = 1001。累积确认只推进到“连续收到的最后一个字节”之后，2001–3000 的到达不会让 ack 前移。

3. 现代 Linux 的初始拥塞窗口大约是多少？依据哪个 RFC？

约 10 个 MSS（≈14600 字节），依据 RFC 6928；Linux 3.0+ 默认如此。RFC 5681 的上限是 4 个 MSS，属更早的规定。

4. 为什么 UDP 不存在“粘包”问题？

UDP 保留报文边界：一次发送对应一个数据报，接收方按数据报交付。注意接收缓冲区不足时数据报会被截断，超出部分丢弃。

5. 服务端出现大量 CLOSE_WAIT，最可能的原因是什么？

应用收到 FIN 后没有调用 close()（连接泄漏、异常分支未释放），属于代码问题，调内核参数无效。
