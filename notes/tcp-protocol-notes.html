01五分钟速览Seven conclusions · Seven anchors

七条结论加七个锚点，先背熟。细节留到后面按需回查，不必一次读完。

一句话定义：传输控制协议（Transmission Control Protocol，TCP）是 TCP/IP 模型传输层上面向连接的、可靠的、基于字节流的传输协议。向上，它给应用提供进程到进程的通信；向下，它把字节交给 IP 逐跳转发。

连接是逻辑的没有物理链路。两端各自维护一套状态机：序列号、窗口、定时器、缓冲区。
建立三次，释放四次本质是「双向 ISN 同步」与「双向关闭通知」必须各自完成一遍。
可靠四件套序列号定位、ACK 确认、超时重传补救、校验和查错。缺一样都不成立。
字节流不是消息流TCP 不保留应用层消息边界，粘包与拆包只能由应用层解决。
两层窗口接收方给的 rwnd、发送方算的 cwnd，任一时刻的在途上限 = min(rwnd, cwnd)。
流控与拥塞是两件事一个防压垮接收方，一个防压垮网络。目标不同，机制独立。
可靠不等于实时保证有序、不丢、不重，但延迟抖动与队头阻塞是它的结构性代价。

02定位与术语Where TCP sits

TCP 解决的是「进程到进程」的可靠传输：端口定位进程，IP 负责逐跳转发。

应用层HTTP / FTP / SSH
传输层TCP / UDP
网络层IP
链路层Ethernet / Wi-Fi

TCP 对上层提供进程到进程的通信能力——靠端口号区分进程；对下把数据交给 IP，由 IP 负责逐跳转发。所以「端口」想进程，「IP」想主机与路由，两者分工不重叠。

03四个核心特点Connection · Reliability · Byte-Stream · Duplex

四个特点不是四个并列功能，而是同一套机制在不同侧面上的样子。

面向连接 Connection-Oriented

  • 通信前必须三次握手建立连接，通信结束后通常四次挥手释放。
  • 「连接」是逻辑连接：没有物理线路，只体现为两端各自维护的状态机——序列号、窗口、定时器、缓冲区。
  • 一条连接由四元组唯一确定：(源 IP, 源端口, 目的 IP, 目的端口)。

可靠传输 Reliable

  • 确认机制：接收方对已正确收到的数据回 ACK。
  • 超时重传：RTO 到期仍未收到 ACK 就重传。
  • 序列号：检测丢失、乱序、重复。
  • 校验和：检测传输过程中的比特错误。
  • 在此之上还有快速重传与 SACK 提升恢复效率，见第 6 节。

基于字节流 Byte-Stream

  • TCP 把应用层数据看作无结构的字节序列，不保留任何消息边界。
  • 发送方有发送缓冲，接收方有接收缓冲；应用层的 write() 与网络上的分段是解耦的。
  • 由此产生两个现象：粘包（多次 send 被合并进一个报文段）与拆包（一次 send 被切成多段）。
  • 这类问题只能由应用层解决：定长、分隔符、长度字段，或者换用自带边界的协议。

全双工 Full-Duplex

  • 双方可以同时发送与接收。
  • 两个方向各自独立维护序列号、窗口与定时器，所以关闭也必须两个方向分别关闭——这正是四次挥手与半关闭的根源。

半关闭 Half-Close

  • FIN 的语义是「我这个方向没有数据要发了」，不是「连接断了」。
  • 发完 FIN 的一方仍可继续接收，这种状态叫半关闭。
  • 编程接口：shutdown(fd, SHUT_WR) 只关闭写方向并发 FIN；close(fd) 关闭整个描述符。
  • HTTP/1.0 短连接、FTP 数据连接都是先半关闭、再等对端收尾。
校正「必须四次挥手」是教学简化

挥手次数取决于双方当时是否还有数据要发。若被动方已无数据可发，ACK 与 FIN 可以合并成一个报文段，实际呈现为三次挥手。所以「四次」是常见形态，不是协议强制次数。

记住全双工是四次挥手与半关闭的根源：两个方向各自独立关闭。

04三次握手Three-Way Handshake

核心不是「打招呼」，而是双向同步 ISN 并锁定参数。第三次 ACK 是唯一能顺手带数据的握手报文。

  • 第1步的 SYN 消耗1 个序列号，所以第2步回 ack = x + 1。
  • 第2步的 SYN 同样消耗 1 个，所以第3步回 ack = y + 1。
  • 第3步的 ACK 报文可以携带数据，这是唯一能「顺手带一趟」的握手报文。

为什么必须是三次

同步双向 ISN双方都要知道对方从哪个号开始，且都需要对方对自己 ISN 的确认。两次只能完成一个方向。
确认双向可达客户端能确认「服务端能收也能发」，服务端也能确认「客户端能收也能发」。
防历史失效请求一个早已失效的重复 SYN 若到达服务端，两次握手会让它直接建连并空等，白占资源；三次握手下客户端不会回 ACK，连接建不起来。
协商参数MSS、窗口扩大因子、SACK、时间戳都只在 SYN 中交换，连接建成后无法再改。

结论两次不够，四次多余。三次是「双向同步 + 双向确认」的最小完备次数。

参数协商与安全细节

  • ISN 随机化：现代实现用随机或时钟驱动的 ISN，降低序列号预测攻击与旧连接干扰。RFC 6528 给出基于 SipHash 的生成算法。
  • 两个队列：Linux 分 SYN queue（半连接队列，tcp_max_syn_backlog）与 accept queue（全连接队列，somaxconn）。SYN Flood 打满半连接队列，可用 SYN Cookie（tcp_syncookies）应对。
  • TCP Fast Open：RFC 7413，允许 SYN 携带数据，省掉一次 RTT；需双方支持且受安全策略限制。

05四次挥手Four-Way Teardown

挥手次数取决于双方是否还有数据要发：能合并就是三次，通常呈现为四次。

  • FIN 也消耗 1 个序列号，所以对方回 ack = u + 1。
  • 第2步 ACK 与第3步 FIN 通常分开：全双工下，「我收到你要关」与「我也发完了」是两件独立的事。
  • 第3步的 seq 记为 w：被动方在这期间若发过数据，序列号已经推进。

TIME_WAIT 的两个作用

  1. 保证最后一个 ACK 能到达：若第4步 ACK 丢失，被动方会重传 FIN；此时主动方还在 TIME_WAIT，能再应一次 ACK。若已关闭，重传的 FIN 只会收到 RST，对端异常终止，可能截断数据。
  2. 让旧连接的残余报文消散：等满 2MSL，确保本连接的迷路报文全部过期，不会被同一四元组的新连接误收。
校正两个最常被记反的点

一、TIME_WAIT 只有主动关闭方有。被动方走 CLOSE_WAIT → LAST_ACK → CLOSED。大量 TIME_WAIT 说明本机是主动关连接的一方（客户端或短连接服务器）；大量 CLOSE_WAIT 说明本机应用没正确 close()，那是代码问题，调内核参数无效。

二、2MSL 不是固定 2 分钟。RFC 793 建议 MSL = 2 分钟，但 Linux 把 TIME_WAIT 固定为 60 秒（TCP_TIMEWAIT_LEN），与 RTO 无关；net.ipv4.tcp_fin_timeout 管的是 FIN_WAIT_2 的停留时间。高并发下可用 tcp_tw_reuse 缓解（仅对主动发起连接的客户端方向安全），tcp_tw_recycle 已在 Linux 4.12+ 移除，不要再用。

为什么是四次不是三次

  • 全双工：两个方向的关闭互不依赖。被动方收到 FIN 时可能还有数据没发完，只能先 ACK 说「我知道了」，等发完再 FIN。
  • 若被动方恰好也没数据要发，ACK 与 FIN 可合并，形式上就变成三次。所以「四次」是常见形态，不是协议强制。

06可靠传输Sequence · ACK · Retransmit · Checksum

可靠性由四组机制叠加而成：序号定位、ACK 确认、重传补救、校验和查错。缺一样都不成立。

序列号与确认号

  • 序列号是字节级编号，不是报文编号：seq = 本报文第一个数据字节的编号。
  • ack = 期望收到的下一个字节编号，即累积确认。
  • 因此 ACK 具有累积性：一个 ACK 确认了此前所有字节；乱序到达的字节不会让 ACK 前移。
  • 32 位序列号会回绕；在高带宽时延积（BDP）链路上回绕更快，需靠时间戳选项做 PAWS 判别。

→ ack
ack = 1001期望的下一字节
收到 1 – 1000 与 2001 – 3000中间有空洞
→ ack
ack 仍 = 1001累积确认不跨空洞；SACK 可在选项里告知 2001–3000

易错ack 是「我期望的下一个字节」，不是「我已收到的最后一个字节」。差 1 是经典失分点。

超时重传 RTO

  • RTO 由 RTT 采样动态估算（Jacobson / Karels 算法）：平滑值 SRTT 加偏差 RTTVAR，并做上下界约束；Linux 下限常为 200 ms（TCP_RTO_MIN）。
  • Karn 算法：重传过的报文不做 RTT 采样（重传会让 ACK 归属产生歧义），配合时间戳选项可放宽。
  • 指数退避：连续超时按 1、2、4、8 倍递增 RTO，避免拥塞时越丢越猛。
  • 两种触发：超时重传（RTO 到期，通常是严重丢包或 ACK 全丢）与快速重传（重复 ACK 达阈值，不等超时）。

快速重传与 SACK

  • 触发条件：同一 ack 号累计出现 4 次（即收到 3 个重复 ACK）时，判定该段丢失并立即重传；阈值 dupthresh 可调，Linux 另有 tcp_reordering 容忍乱序。
  • SACK（RFC 2018）：在选项里标明「我已收到哪些块」，发送方精确重传缺口，避免 go-back-N 式的重复发送。配套 DSACK 识别重复报文。
  • RACK / TLP：Linux 现代实现基于时间而非 ACK 计数判断丢包，在「每窗口丢包少」的场景更准。

校验和 Checksum

  • 16 位反码求和，覆盖伪首部 + TCP 首部 + 数据 + 填充。
  • 伪首部含源 / 目的 IP，所以重算校验和必须知道 IP 层信息——NAT 改写地址时要同步更新。
  • 只检错，不纠错。检测到错误直接丢弃，靠重传补救。
校正校验和的适用范围

TCP 校验和在 IPv4 与 IPv6 下都是必需的。「IPv6 中校验和可选」只适用于 UDP（RFC 8200）。另外，校验和挡不住恶意篡改，安全要靠 TLS / IPsec。

可靠性 ≠ 实时性

TCP 保证的是最终正确、有序、不重复，为此会等待与重传，代价是延迟可能突增（典型是尾部丢包导致的等待）。这正是实时业务转向 UDP / QUIC 的原因。

07流量控制Flow Control

流量控制是接收方对发送方的限速通知，靠 rwnd 与滑动窗口实现。零窗口时必须探测，不能静默。

滑动窗口

接收方在每个 ACK 里携带窗口字段 rwnd，声明「从当前 ack 号起还能再收多少字节」，发送方据此限制在途数据量。

零窗口与窗口探测

  • rwnd = 0 时发送方暂停发送新数据，但不能就此静默：需启动持续定时器，周期性发送零窗口探测。
  • 接收方窗口恢复后回一个带非零窗口的 ACK，发送方据此恢复。
  • 探测报文本身不算新数据，避免双方互等造成死锁。

补一句「窗口为 0 就停止发送」只停了新数据；探测报文与已发出数据的重传仍然继续。

窗口扩大选项

  • 首部窗口字段只有 16 位，最大 65535 字节，对高 BDP 链路远远不够。
  • 窗口扩大选项（RFC 7323）给出移位因子 0–14，实际窗口 = 字段值 × 2shift，理论上限约 230 字节（1 GiB）。
  • 只能在 SYN 中协商，两个方向各自生效，连接期内不可改。

糊涂窗口综合症 SWS

  • 接收方每次只腾出很小空间就通告小窗口，或发送方只发很小的数据，结果是大量小报文，效率极低。
  • 对策：接收方延迟通告直到窗口够大（或达到半个缓冲）；发送方用 Nagle 算法合并小数据。
  • 注意 Nagle 与延迟 ACK 组合可能引入约 40 ms 级延迟，交互型小包场景要考虑关掉。
rwnd接收方通告：缓冲区还能收多少
取小 →
cwnd发送方推算：网络还能承载多少
= 上限
在途字节数任一时刻已发未确认的数据量

记住两个窗口目标不同：rwnd 防压垮接收端，cwnd 防压垮网络。发送方只能取较小值。

08拥塞控制Congestion Control

拥塞控制是发送方对网络的试探：慢启动指数探路，拥塞避免线性增长，一旦丢包就减半回退。

阶段触发cwnd 变化
慢启动 Slow Start连接开始，或超时后重开每收到一个 ACK 加 1 MSS，等效每 RTT 翻倍（指数）
拥塞避免 Congestion Avoidancecwnd ≥ ssthresh每 RTT 加 1 MSS（线性，加法增大）
快速重传 Fast Retransmit收到 3 个重复 ACK立即重传丢失段，不回到慢启动
快速恢复 Fast Recovery快速重传之后ssthresh = cwnd/2，cwnd = ssthresh（RFC 5681），进入拥塞避免

AIMD 锯齿：加法增大、乘法减小。拥塞避免阶段每 RTT 加 1 MSS（加性），一旦探测到丢包就把 cwnd 减半（乘性）。一增一减形成稳定锯齿，也让多条流最终收敛到大致公平的份额。

关于初始拥塞窗口

校正「从 1 个 MSS 开始」是历史描述
  • RFC 5681 允许初始窗口 IW = min(4·SMSS, max(2·SMSS, 4380 字节))，即最多 4 个 MSS。
  • RFC 6928 提升到 10 个 MSS（约 14600 字节），已是主流实现默认值（Linux 3.0+）。
  • 现代实现第一步通常还做分批发（pacing / 限制初始突发），避免一次性打出 10 个包造成丢包。
  • 初始 ssthresh 不是固定常数：RFC 5681 建议设为「任意大」，具体各实现不同。

现代算法

算法思路特点
Reno / NewReno基于丢包，AIMD经典教科书模型，高 BDP 下恢复慢
CUBIC（RFC 9438）以时间为自变量的三次函数增长Linux 默认，与 RTT 弱相关，高速链路表现好
BBR模型驱动，测量瓶颈带宽与最小 RTT不把丢包当信号，高丢包链路吞吐更稳；公平性仍有争议
Vegas / Veno以 RTT 增长为信号更早退让，适合低缓冲网络
校正「TCP 在高延迟高丢包下吞吐受限」太笼统

这个结论主要针对传统 loss-based 算法（Reno 一类）。CUBIC 已显著改善高 BDP 场景，BBR 在高丢包链路上表现更好。现在的瓶颈更多来自算法选择与参数配置，而不是 TCP 协议本身。

记住慢启动其实不慢——它是指数增长。初始窗口已经是 10 个 MSS，不是 1 个。

09报文段结构Segment Format

校正两个尺寸问题

一、「首部固定 20 字节」应为「最小 20 字节」。20 是不含选项时的最小长度；含选项最大 60 字节，因为 4 位数据偏移最多表示 15 × 4 = 60。

二、控制位是 8 个，不是「SYN、ACK、FIN、RST、PSH、URG 等」。RFC 9293 定义了 8 位，早期 6 位保留字段已被拆出 ECE / CWR 使用；NS 位（RFC 3540）于 2017 年被 RFC 8311 废弃，所以现在是 4 位保留。

10与 UDP 的对比TCP vs UDP

TCP 用开销换可靠，UDP 用放弃保证换低延迟；QUIC 把可靠性搬进用户态，绕开了 TCP 层的队头阻塞。

记住要可靠有序选 TCP；要低延迟、能容忍丢包或需要组播选 UDP；两样都要，就看 QUIC。

11场景与局限When to use, when to leave

判断该不该用 TCP，只问两件事：能否容忍建连与重传带来的延迟，是否需要绝对的正确与顺序。

适合的场景

  • Web：HTTP/1.1、HTTP/2、HTTPS（TLS over TCP）。
  • 文件与邮件：FTP、SFTP、SMTP、IMAP / POP3，需要完整性。
  • 远程管理：SSH、Telnet（不推荐）、RDP。
  • 数据库与中间件：MySQL、PostgreSQL、Redis，长连接、请求—响应。
  • 服务间调用：gRPC（HTTP/2 over TCP）。
  • 共性：能容忍一定延迟，但对正确性与顺序敏感。

局限

  • 建连开销：三次握手至少一个 RTT，TFO 可省。
  • 队头阻塞：一个报文段丢失，后续已到达的数据也不能交付应用。HTTP/2 的多路复用仍受 TCP 层 HOL 制约，这是 HTTP/3 改用 QUIC 的直接原因。
  • 拥塞算法的差异：loss-based 算法在高丢包链路吞吐受限；跨运营商、长肥管道（LFN）对窗口与算法都很敏感。
  • 不保证实时：重传与排队带来延迟抖动，不适合强实时。
  • 状态开销：每条连接占用内核内存与一个四元组，海量短连接会耗尽端口并堆积 TIME_WAIT。

补一句「不适合短连接高频交互」是相对结论，不是禁令：keep-alive、连接池、TFO、HTTP/2 多路复用都能缓解。

什么时候换 UDP / QUIC

  • 实时音视频、实时游戏、直播：能容忍少量丢包，只追求低延迟 → UDP 或 QUIC。
  • 需要自定义重传 / 拥塞策略（自研可靠传输）→ 基于 UDP 实现。
  • 需要穿透 NAT、免握手、自带加密 → QUIC。

十个高频易错点

✗

ack 是已收到的最后一个字节　ack 是期望的下一个字节，差 1 就是失分点。

SYN / FIN 不占序号　两者各消耗 1 个序列号，所有 +1 关系由此而来。

✗

✗

✗

✗

✗

面试高频问法

问题答题骨架
为什么三次握手不是两次？双向 ISN 同步 + 双向可达确认 + 防历史失效 SYN；两次只能完成单向同步。
为什么四次挥手？全双工两个方向独立关闭；被动方可能还有数据，ACK 与 FIN 只能分开。
TIME_WAIT 的作用？保证最后一个 ACK 可达（对端重传 FIN 能应答）+ 让旧报文消散，避免端口复用串扰。
大量 TIME_WAIT 怎么办？先判断是否正常（本机主动关闭多）；tcp_tw_reuse（客户端方向安全）、缩短 keep-alive、改用长连接与连接池。
大量 CLOSE_WAIT 怎么办？应用收到 FIN 后没有 close，查代码：连接泄漏、异常分支未释放。
粘包怎么解决？TCP 是字节流无边界；应用层用定长、分隔符、长度字段，或换带边界的协议。
流控和拥塞控制怎么区分？前者防接收端溢出（rwnd，接收方通告），后者防网络过载（cwnd，发送方推断）。
快重传与快恢复的区别？快重传是「立即重传丢包」，快恢复是「重传后不回慢启动，cwnd 减半后继续线性增长」。
长肥管道为什么慢？窗口不足 + RTT 大；需要窗口扩大、合适的拥塞算法（CUBIC / BBR）与更大的缓冲。
TCP 与 UDP 怎么选？要可靠有序 → TCP；要低延迟、可容忍丢包或组播 → UDP；折中看 QUIC。

四组易混概念

rwnd ≠ cwnd
rwnd 是接收方通告的能力上限，cwnd 是发送方对网络的估算，实际可发取两者较小值。
TIME_WAIT ≠ CLOSE_WAIT
前者是主动关闭方的正常等待（2MSL）；后者是被动方应用还没调用 close()，属于代码问题。
FIN ≠ RST
FIN 是「我这个方向不发数据了」，可半关闭后继续接收；RST 是直接重置连接，数据可能被丢弃。
累积确认 ≠ SACK
累积 ACK 只推进到连续收到的末尾；SACK 在选项里额外告知已收到的离散块，用于精确重传。

答法先给结论，再补一句机制原因，最后点出常见误区——三句话足够，不要从头讲一遍协议。

14自测十题Self-Test

先合上笔记，用纸笔写出关键数字与状态名，再逐题点开对照。打印时会自动展开全部答案。

01三次握手中，客户端发 SYN(seq=x)，服务端回 SYN+ACK(seq=y, ack=?)，客户端再回 ACK(ack=?)。填空，并说明 SYN 为什么占一个序列号。

ack = x+1；ack = y+1。SYN 是「同步序列号」的报文，本身要占一个序号位置，才能与后续数据字节的编号连续、并让对方的确认有明确指向。SYN 与 FIN 都属于「消耗序列号的控制报文」。

02从「双向 ISN 同步」的角度解释：为什么两次不够、四次多余？

两次握手只能完成单向同步：服务端知道了客户端的 ISN，但客户端无法确认自己的 ISN 是否被收到、也不知道服务端的 ISN 是否被正确确认。三次实现「双向同步 + 双向可达确认」；第四次没有额外信息可交换——第三个 ACK 已同时完成「确认对端 SYN」和「自己的参数已被接收」。

03四次挥手中，为什么 ACK 与 FIN 通常分开发送？什么情况下退化为三次？

TCP 全双工：被动方收到 FIN 只代表「对端不再发送」，自己可能还有数据在发，所以只能先 ACK；数据发完才发 FIN。若被动方当时已无数据可发、且无需等待应用处理，ACK 与 FIN 可合并为一个报文段，表现为三次挥手。

04TIME_WAIT 出现在哪一方？两个作用是什么？Linux 上实际时长多少？tcp_fin_timeout 管的是哪个状态？

只出现在主动关闭方（先发 FIN 的一方）。作用：1 若最后 ACK 丢失，对端重传 FIN 时还能应答，避免对端收到 RST 而异常关闭；2 等待 2MSL 让本连接的残余报文消散，防止相同四元组的新连接误收旧报文。Linux 实际固定 60 秒，与 RTO 无关。tcp_fin_timeout 影响的是 FIN_WAIT_2。

05什么是半关闭？Socket 编程里怎么实现？它和 close() 有什么区别？

半关闭指一方关闭发送方向（发 FIN）但仍可继续接收对端数据，状态上表现为主动方 FIN_WAIT_2、被动方 CLOSE_WAIT。实现用 shutdown(fd, SHUT_WR)。close() 关闭整个描述符（两个方向并释放 fd），shutdown 只影响数据流方向、不释放描述符。

06接收方收到序号 1–1000 后应回 ack 多少？若收到 1–1000 与 2001–3000（中间缺失）呢？为什么？

正常回 ack = 1001。有空洞时累积确认仍回 1001（除非启用 SACK，在选项里告知已收到 2001–3000）。因为累积 ACK 只推进到「连续收到的最后一个字节之后」。

07发送方同时有 rwnd = 8000、cwnd = 3000（字节），此刻最多能发多少未确认数据？为什么取小？

最多 3000 字节。rwnd 是接收端能力上限，cwnd 是发送方对网络容量的推断，在途数据必须同时满足两者，所以取 min。

08快重传的触发条件是什么？快恢复后 cwnd 与 ssthresh 如何设置（RFC 5681）？RTO 超时又会怎样？

触发条件：收到 3 个重复 ACK（同一 ack 号累计 4 次，阈值 dupthresh 可调）。快恢复：ssthresh = max(FlightSize/2, 2·MSS)，cwnd = ssthresh（+3 MSS 的变体也存在），随后进入拥塞避免。若发生 RTO 超时：ssthresh = cwnd/2，cwnd 重置为 1 MSS（现代实现按 IW 重启），重新进入慢启动。

09接收窗口通告为 0 后，发送方可以完全静默吗？不能的话靠什么恢复？

不能静默。发送方启动持续定时器，周期性发送零窗口探测；接收方窗口恢复后回一个带非零窗口的 ACK，发送方据此恢复发送。

10首部最小 / 最大长度各是多少？4 位数据偏移为什么最大只能表示 60 字节？窗口扩大选项能把窗口放大到什么量级？

最小 20 字节，最大 60 字节。数据偏移以 4 字节为单位（值 5–15），15 × 4 = 60。窗口扩大因子最大 14，65535 × 2^14 ≈ 2^30 字节，约 1 GiB。

11为什么 UDP 不存在「粘包」问题？

UDP 保留报文边界：一次发送对应一个数据报，接收方按数据报交付。注意接收缓冲区不足时数据报会被截断，超出部分丢弃。

12服务端出现大量 CLOSE_WAIT，最可能的原因是什么？

应用收到 FIN 后没有调用 close()：连接泄漏、异常分支未释放。属于代码问题，调内核参数无效。

15动手验证Verify on a real box

概念记住之后，用几条命令验证最有效：先看状态分布，再抓一次握手，最后核对内核参数。

查看连接与状态

Bash
# 连接状态汇总

# 单条连接的定时器、窗口、拥塞信息

# 各状态数量（TIME_WAIT / CLOSE_WAIT 排查）

Bash

关键内核参数

Bash

排查顺序

  1. 看状态分布：ss -tan 统计各状态数量。TIME_WAIT 多说明本机主动关闭多；CLOSE_WAIT 多直接去查代码。
  2. 看监听队列：ss -lnt。监听套接字的 Recv-Q 是当前全连接队列长度，Send-Q 是 backlog 上限；Recv-Q 长期贴着 Send-Q，说明 accept 跟不上。
  3. 抓握手：tcpdump -n -i any 'tcp[tcpflags] & tcp-syn != 0'，确认三步齐全、seq / ack 满足 +1 关系。
  4. 核对参数：sysctl net.ipv4.tcp_congestion_control net.core.somaxconn net.ipv4.tcp_max_syn_backlog。

注意命令与字段含义以 Linux 为准，其他系统命令不同，但观察目标一致。

7「确认机制 ACK」ACK 是累积确认，含义为「期望的下一个字节」；普遍启用延迟确认
8快重传「收到 3 个重复 ACK」更精确：同一 ack 号累计 4 次，阈值 dupthresh 可调；现代实现另有 RACK / TLP
9窗口为 0 时停止发送停的只是新数据；探测报文与重传继续，靠持续定时器恢复
10首部固定 20 字节最小 20、最大 60（数据偏移 4 位、单位 4 字节）
11标志位「SYN、ACK、FIN、RST、PSH、URG 等」RFC 9293 共 8 位，含 ECE / CWR；NS 位已废弃（RFC 8311）
12校验和描述笼统覆盖伪首部；IPv4 / IPv6 下 TCP 校验和均为必需（IPv6 可选仅指 UDP）
13序列号检测丢失和乱序补充：32 位序号会回绕，高 BDP 需时间戳做 PAWS；SACK 用于精确重传
14拥塞控制偏保守，高延迟高丢包吞吐受限该结论主要针对 loss-based 算法；CUBIC（Linux 默认）/ BBR 已明显改善
15不适合短连接高频交互缓解手段：keep-alive、连接池、TFO（RFC 7413）、HTTP/2 多路复用（TCP 层 HOL 仍在）
16三次握手的目的是「确认双方收发能力」核心是双向 ISN 同步 + 参数协商（MSS / 窗口扩大 / SACK / 时间戳），确认可达是附带结论
17未提 MSS 默认值未协商时默认 536 字节；取双方通告的较小值；MSS = MTU − 40
