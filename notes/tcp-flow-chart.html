accept() 之后的三种并发模型

三条路径解决的是同一个问题：一个监听 fd 要同时服务多个连接。差别在于「谁来做调度、单机能扛多少连接」。

路径 A

多线程 / 多进程

accept() 拿到 connfd 后交给独立线程或进程（或线程池 / 进程池），一个连接一条执行流。阻塞式代码可直接复用，适合连接数不大、单连接耗时长的场景（文件传输、数据库代理）。

路径 B

IO 多路复用（select / epoll）

少量线程用事件循环同时监控大量 fd，就绪才处理。适合连接多、单次交互轻的高并发网关与聊天服务；Linux 首选 epoll（select 受 FD_SETSIZE 限制且需线性扫描）。

路径 C

协程（goroutine / asyncio）

用同步写法获得异步调度，阻塞点由运行时让出。适合海量并发 + 业务逻辑复杂的服务；注意一次真正的阻塞调用（如同步 IO、长计算）会卡住整个调度线程。

关键坑（对应图中 ①–⑤）

这五处是最容易在联调与压测中翻车的地方，编号与图上标记一致。

1

backlog 不是「最大连接数」

listen(fd, backlog) 只是内核连接队列的上限提示，实际取 min(backlog, somaxconn)，并受 tcp_max_syn_backlog 影响。队列满后，握手完成的连接也会被丢弃，表现为「连得上却偶发超时」。

2

accept() 返回的是新 fd

监听 fd 只负责接新连接，永远不用于收发；每次 accept 返回一个独立的 connfd，靠四元组区分。忘记 close(connfd) 会累积 CLOSE_WAIT 并最终耗尽 fd。

3

TCP 没有消息边界

一次 recv 可能拿到半条消息，也可能拿到多条拼在一起。必须由应用层用「定长 / 分隔符 / 长度字段」界定边界，不能假设「一次 recv = 一条消息」。

4

send() 可能只发出去一部分

返回值是实际写入的字节数，可能小于请求长度（发送缓冲满、被信号打断、非阻塞返回 EAGAIN）。必须按返回值推进偏移并循环发送，直到写完或明确失败。

5

TIME_WAIT 在主动关闭方

谁先 close() 谁进 TIME_WAIT（Linux 固定等待 60 s）。TIME_WAIT 多说明本进程在主动关连接，一般是正常现象；大量 CLOSE_WAIT 才是「代码没 close」的信号。

技术基准：RFC 9293（取代 RFC 793）、Linux 内核 TCP 实现。状态徽标指内核状态，与 API 调用一一对应：listen() → LISTEN，connect() → SYN_SENT → ESTABLISHED，close() 的走向取决于谁是主动关闭方。
